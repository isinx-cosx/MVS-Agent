# MVS Agent

通用 Agent 内核。当前八个层次：

- **模型层** —— 请求进，事件流出
- **工具层** —— 读/写/创建/删除文件 + 执行命令
- **恢复层** —— 每次变更型工具调用前后对整棵树做基线快照，可撤销
- **权限层** —— 模式能力上限 + 熔断器 + 规则 + 抗疲劳
- **上下文层** —— token 估算与两级压缩
- **运行时** —— 会话、agent 循环、事件流、检查点、中断恢复
- **传输层** —— 本地 HTTP + WebSocket，四道防护默认开启
- **开发页** —— 一张验证边界的体检表（**不是产品 UI**）

```bash
npm run fake              # 终端 1：本地假模型端点，不花钱
npm run serve:fake        # 终端 2：启动运行时，打印带令牌的地址
node scripts/demo-compaction.ts   # 看压缩做了什么
```

尚未构建：产品 UI、真正的沙箱（权限层不是沙箱）、事件溯源（**刻意不做**）。见文末「尚未构建」。

> 调研结论见 `docs/sandbox-platform-matrix.md`（现有产品在 Windows 上怎么做沙箱）
> 与 `docs/design-notes-sandbox-permissions-reversibility.md`（沙箱/权限/可逆性三层设计）。

# 模型层

## 三条不可动摇的设计决定

### 1. 流式是原语，不是可选功能

`ModelClient` 只有一个方法：

```ts
stream(req: ModelRequest): AsyncIterable<ModelEvent>
```

阻塞式是它的**派生物**（`collect()` 把 delta 收干），不是第二套实现。

理由：字符串随时能从流里塌缩出来，反过来不行。一旦接口暴露成 `Promise<string>`，以后想加流式就要改穿每一层——UI、日志、超时、事件日志全要动。

`src/cli/chat.ts` 是这条决定的证明：它直接消费 `stream()`，边到边渲染，**不走 collect**。

### 2. 能力缺失是可观测的降级，不是崩溃

不同兼容端点的能力不一致：有的不给 `usage`，有的不给 `reasoning_content`，有的不发 `[DONE]`。所以 `Notice` 是一等事件，上层永远不许假设某个字段一定存在。

### 3. 错误是一等事件，不是异常

流吐了 200 个字以后连接断掉——这不是 `throw` 的场合，而是状态机里的一种正常终止。上层必须能区分「没开始」和「吐了一半」。

```ts
type ModelEvent =
  | { type: 'text_delta';      text: string }
  | { type: 'reasoning_delta'; text: string }        // DeepSeek 的思维链
  | { type: 'tool_call_delta'; index: number; id?: string; name?: string; argsJsonDelta?: string }
  | { type: 'usage';           usage: Usage }
  | { type: 'notice';          notice: Notice }      // 降级提示
  | { type: 'done';            reason: FinishReason }
  | { type: 'error';           error: ModelError }
```

两个易踩点：

- **`tool_call_delta` 是 JSON 碎片，不是完整 JSON。** 参数按 `index` 分组、跨 chunk 累积，拼完才可能合法。
- **`[DONE]` 不是 JSON**，要在解析前拦掉。

# 工具层

## 边界：模型**能**拿到工具，但裸对话 REPL 拿不到

工具确实已经接进模型了 —— 工具循环跑在 `src/host/session.ts`：策略判定 → 需要时挂起等审批 → 写 intent → 执行 → 结算回填。`ToolRegistry.toModelSchemas()` 由会话在每次调模型前调用。

**唯一刻意保持无能力的是 `src/cli/chat.ts`**（裸对话 REPL）：它只连模型，用来单独跑、单独测模型层。这条边界不是靠自觉维持的，有一条可执行的守卫测试：

```
✔ 结构守卫：CLI 对话 REPL 保持无能力（不引用工具/恢复/权限/运行时）
```

它断言 `chat.ts` 不引用那五层，且 `createDefaultRegistry` / `createRecovery` / `new Policy(` / `new Session(` / `new HostServer(` 只出现在人工调用入口和 `src/{recovery,policy,host,protocol}/` 里。

⚠️ 注意这个测试**不**保证「模型拿不到能力」——`src/host/` 整个目录都在白名单里，因为工具循环就在那儿。它保证的是那个裸 REPL 不会随手把能力拽进来，从而让模型层保持可独立验证。

## 八个工具

| 工具 | risk | 说明 |
|---|---|---|
| `read_file` | read | 全文或按 `offset`/`limit` 行切片 |
| `write_file` | write | 覆盖写入，父目录自动创建 |
| `create_file` | write | **已存在则拒绝**（防误覆盖），父目录自动创建 |
| `delete_file` | write | 目录必须显式 `recursive: true`，不接受默认递归 |
| `run_command` | execute | 退出码 + stdout + stderr，带超时与取消；`background: true` 立刻返回作业 id |
| `list_jobs` | read | 后台作业列表与是否还在跑 |
| `job_output` | read | 某个作业的 stdout/stderr 尾部 |
| `kill_job` | read | 停掉一个作业（连整棵进程树） |

后三个标成 `read` 是有意的：它们只能看注册表，或者停掉**我们自己起的**作业 ——
`kill_job` 只接受注册表里的 id，**不能按 pid 杀任意进程**。那是它敢标成 read 的全部理由。
把它标成 `execute` 会让「停掉我自己起的 dev server」也要求人确认一次，那是没必要的摩擦。

`risk` 字段现在被权限层读了：它是能力上限判定和只读分类器的输入。

## 后台命令，以及它**破坏**了什么

`run_command background=true` 用于不会自己退出的命令（`npm run dev`、`watch`）。
它立刻返回一个作业 id，之后用 `list_jobs` / `job_output` / `kill_job` 管理。

⚠️ **它和恢复层之间有一个真实缺口，我们选择承认它而不是假装覆盖。**

恢复层的快照边界是「动作前 → 动作后」。后台命令在 after 快照取完之后**还在写文件**。
如果此时照常提交事务，后果不是「撤销不太准」，而是很具体的一种事故：下一个工具调用的
事务会把后台进程刚生成的产物算成「自己新增的」，于是**撤销那一步会删掉后台的产物**。
copilot-cli#1675 就是这一类 —— 回滚函数执行 `git clean -fd`，删掉了约 1GB
agent 只「读过」的未跟踪产物。

所以 `RecoveryGuard` 有两条显式规则：

1. **后台启动本身不产生事务** —— after 快照此刻拍到的是「还没开始干活」，给它一个
   事务等于给用户一个点了没用的撤销按钮。
2. **只要有作业在跑，同一工作区的文件改动一律不产生撤销条目** —— 那个时间窗里的
   归属根本无法确定。

取舍和「无变化不产生条目」是同一条：**没有 > 有但不对。**

权限层另外加了一条：**后台命令不适用只读自动放行**，即使命令文本可证明只读。
「只读」是关于**命令文本**的判定，而后台命令的风险来自**时间**。这条只影响
`workspace-write` 下的默认行为；`full-access` 下不额外加询问 —— 那个模式的语义
就是「不要问」，偷偷多问一次会让模式的定义不可信。

## 三条原则

### 1. 错误是结果，不是异常

工具内部该 throw 就 throw（那是最自然的写法），但**边界**在 `ToolRegistry.execute` 收敛：任何异常都变成 `ToolResult`。

模型报错要能回填给它自己修正。`throw` 会让整个循环死掉。

错误类型是机器可读的，不是一句字符串：

```
unknown_tool · invalid_args · not_found · already_exists · outside_root
is_a_directory · not_a_directory · aborted · timeout · sandbox · failed
```

### 2. 参数是不可信输入，且 schema 是单一事实来源

每个工具的 `parameters` 字段**既是发给模型的声明，也是运行时的校验依据**。两处分开写必然漂移。

校验器是手写的 JSON Schema 子集（`type` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `minimum` / `maximum` / `minLength`）——为了几个字段拉 ajv 进来不划算。

### 3. 路径围栏是工具的固有属性，不是「以后加的策略」

所有文件工具的路径都经过 `resolveInsideRoot`。这不是可插拔的安全层，而是**工具如何解析路径的定义**——事后补要重写每个工具实现。

拦两类逃逸：

1. **文本逃逸** —— `../..`、绝对路径、盘符切换
2. **符号链接逃逸** —— 工作区内一个指向外部的软链

第 2 类容易被漏掉：只做字符串前缀检查是不够的，必须对**已存在的最近祖先**做 `realpath` 再检查（路径中间段可能还不存在，那时谈不上软链）。

## 命令工具的两个实测发现

都来自真的跑了一遍，不是推测。

### 一、绝不能用管道 stdio

| stdio 模式 | 结果 |
|---|---|
| `pipe` | **同步抛出 EPERM**（注意是抛异常，不是 error 事件） |
| `fd`（重定向到真实文件） | ✅ 可用，输出完整捕获 |
| `ignore` | ✅ 可用 |

所以输出直接重定向到临时文件（fd stdio），子进程退出后再读。附带好处：绕开了 shell 引号转义这一整类问题。

### 二、沙箱拒绝必须和命令失败分开

`EPERM` 意味着「这条路走不通」，重试同一个命令不会有任何不同结果。如果和「退出码非 0」混为一谈，模型会陷入无意义的重试循环。

所以它们是两个不同的 error kind：`sandbox` 与 `failed`。

# 恢复层

## 为什么它必须在工具分发「之下」

调研里最硬的一条结论（`docs/sandbox-platform-matrix.md`）：

> **从工具级 checkpoint 内部，无法覆盖 shell 通道。**

Claude Code「Bash command changes not tracked」、华为 CodeArts「Bash 命令或外部编辑器做的修改不会被追踪」、Kiro「不追踪 MCP 工具或 bash 命令做的修改」——**三家厂商文档记录着同一个洞**，而且是架构性的。

所有能覆盖 shell 的方案，都把快照边界挪到了 agent 之下。所以这里**不在工具内部记录**，而是在 `RecoveryGuard` 里包住工具分发：

```
动作前整树快照  →  执行工具（含它 spawn 的一切）  →  动作后整树快照  →  求差
```

因此 shell 副作用、代码生成、并发的外部改动，都被同一个边界覆盖。

```bash
node scripts/demo-recovery.ts   # 用 shell 删文件 → 撤销 → 内容一字不差回来
```

## 四条从调研直接搬来的规矩

**1. 没有变化就不产生可撤销条目。**
Claude Code 的 issue #34368 是反面教材：rewind 提供「撤销文件删除」选项，点了什么也不做。**「看起来能救、实际救不了」比没有更危险**，所以从源头不产生这种条目。

**2. 冲突时拒绝，而不是覆盖。**
目标文件在这次动作之后被改过 → 跳过并报告 `conflict`，要 `--force` 才覆盖。Aider 的 `/undo` 在五种情况下主动拒绝，评价是：**「这些拒绝是特性——它们防止 undo 吃掉无关的工作。」**

**3. 恢复本身必须可恢复。**
copilot-cli#1675 的教训：那个回滚函数执行 `git reset --hard` + `git clean -fd`，永久删除约 1GB agent 只「读过」的未跟踪产物——**恢复操作本身是一条 shell 命令，而没有任何东西在给 shell 做快照。** 所以每次恢复也创建事务，可以再撤回去。

**4. 如实报告自己的盲区。**
快照记录 `excludedDirs` / `skippedLarge` / `skippedLinks` / `hardLinks`，恢复时一并显示。一份不记录自身盲区的快照，会让人误以为「都能撤」。

## 关键设计选择

| 选择 | 理由 |
|---|---|
| **不尊重 `.gitignore`** | stepback / safesandbox 尊重它，因此漏掉 `.env`、本地数据库、测试数据——而 agent 最容易毁的恰好是这些 |
| **纯文件复制 + `COPYFILE_FICLONE`** | 不依赖 CoW（Windows 上基本不存在：doover 明确不支持原生 Windows，EvoX 写「Windows: ❌ 回落到完整复制」）。一个标志就拿到跨平台优化 |
| **存储目录在工作区之外** | 将来有了写围栏，agent 也碰不到恢复数据 |
| **增量快照** | 用 `size + mtimeMs` 命中上一份快照时复用 hash，一次快照 ≈ 一次目录遍历，而不是重读全树 |
| **内容寻址去重** | 相同内容只存一份 blob |

## 已知边界（不是疏漏，是记录在案）

- **不是备份。** 存储目录与工作区在**同一块磁盘**上，会被同样的灾难影响。上限默认 100 个事务。
- **`size + mtime` 是启发式。** 若文件在同一 mtime 粒度内被改成等长内容会被判为未变（NTFS 粒度 100ns，风险极低，但不是零）。
- **每事务两份快照**（before + after），所以快照文件数是事务数的 2 倍。大工作区下这是真实的内存/磁盘成本。
- **符号链接不跟随**（跟随会逃出工作区），**硬链接无法按路径隔离**（它是文件对象的别名）。两者都被记录为盲区。
- **每个变更型工具调用做两次全树遍历**。大仓库下这会成为瓶颈，需要按目标路径收窄——但收窄需要解析命令，而调研显示解析很脆弱。
- **归属边界：「动作前 → 动作后」这个时间窗内的并发改动会被算进本次事务。**
  快照边界是时间，不是因果。如果在窗口内**有别的东西**也在写同一个目录（用户自己在编辑器里存了盘、另一个终端在跑构建、一个没被收掉的后台进程），
  那些改动既不属于本次工具调用，又会被算进它的 diff —— 于是「撤销下一步」可能顺手动到本属于别人的东西。

  已经做掉的一半：`run_command` 超时/取消时**连整棵进程树一起杀**（Windows 用
  `taskkill /T`，POSIX 给子进程单独开进程组再 `kill(-pid)`）。只杀直接子进程的话，
  它派出去的孙进程会活下来继续写文件，而这些写入正好落在 after 快照**之后** ——
  于是被算进**下一个**事务，用户撤第 3 步、动的却是第 4 步的痕迹。这条有测试钉住，
  而且测试里的孙进程必须**脱离进程组**才有意义（同组的会被 Job Object 连带收掉，
  那样两种实现都能通过）。

  > ⚠️ 测试写法上的这条坑值得单独记：**第一次写的版本（普通孙进程）在没有修复时
  > 也通过**，因为本环境的沙箱把整条父子链放在同一个 Job Object 里，杀父会连带
  > 子孙。一条两种实现都能通过的测试等于没测 —— 是靠「故意退回错误实现看它是否
  > 变红」发现的。

  POSIX 上有个代价必须说清：为了能整组杀，子进程用 `detached: true` 单独开组 ——
  于是它**不再随终端的 Ctrl+C 一起死**。取消改由显式路径负责（守护进程收 SIGINT →
  abort 会话 → 工具收到 abort → `killTree`），而 `process.kill(-pid)` 和
  `spawnSync('taskkill')` 都是**同步**的，所以信号在进程退出前就发出去了，不会漏。

  剩下的一半**没有解**，只能如实说：工具调用窗口内的人为并发写无法归因。
  `guard.ts` 把「并发的改动也被同一边界覆盖」写成了优点 —— 对崩溃恢复是优点，
  对归属是代价。要真正解决，得让文件系统自己带版本（事务性 FS 或内容寻址的工作区），
  那已经不是这一层的范围了。

# 权限层

## 它不依赖沙箱，也替代不了沙箱

调研里有**三个 CVE** 全是同一类——字符串匹配的允许列表被绕过：

| CVE | 绕过方式 |
|---|---|
| [CVE-2025-54131](https://app.opencve.io/cve/CVE-2025-54131) | 反引号 / `$(cmd)` |
| [CVE-2026-22708](https://app.opencve.io/cve/CVE-2026-22708) | shell 内建命令 + 环境变量投毒 |
| [CVE-2026-31854](https://app.opencve.io/cve/CVE-2026-31854) | 网页指令注入（**8.7 High**） |

所以这一层能防的是**手滑**，不是对抗。任何把它当安全边界的文档或 UI 文案都是错的。

它的真正价值是：把「模型想干的事」和「实际允许干的事」分开，并让**每一次拒绝都是机器可读、可解释、可测试的**。

## 求值顺序就是设计

```
1. 能力上限（模式本身）  → 硬拒绝，任何 allow 规则都越不过
1.5 可证明只读的命令     → 自动放行（见下节；判不出来就继续往下走）
2. 熔断器                → 剥夺 allow 规则的批准权，但不强制拒绝
3. 规则                  → deny > ask > allow（具体程度不改变顺序）
4. 默认                  → 按工具风险与工作区内外
5. 降级                  → 熔断命中时 allow→ask；无人可应答时 ask→deny
```

**第 2 步和第 5 步是这一层真正有价值的地方。**

第 1.5 步的位置是有讲究的：它在能力上限**之后**（所以只读模式下 `git status` 照样被拒 ——
那个模式的定义就是「不许执行任何命令」），又在熔断器**之前**（只读命令没碰任何东西，
不该被抗疲劳降级成询问）。

## 减少确认次数：靠「证明只读」，不靠放宽允许列表

出厂允许列表是空的，这是刻意的（Cursor 把 `npm` 整条放进去，而它按前缀匹配 ——
那一条覆盖了 `npm publish` 和**所有 postinstall 脚本**）。代价是 `git status`
这种绝对无害的东西也要点一次确认，而人一旦开始闭眼点「允许」，权限层就形同虚设。

所以补的不是更宽的允许列表，而是一个**能证明只读**的分类器（`src/policy/read-only.ts`）：

- 证明得了 → 自动放行（`reason: 'read-only-command'`）
- 证明不了 → 走原来的流程，照常问

三条硬规矩，都是被 CVE 教出来的：

1. **出现任何 shell 元字符就不认。** `git status && rm -rf /` 和 `git status` 前缀一样 ——
   靠前缀匹配放行就等于把整条链放行了。连引号都不接受：不做引号解析，就不会有引号解析的 bug。
2. **不做前缀匹配，做「程序 + 子命令 + 参数形状」的匹配。** `npm` 单独一条会吞掉 `npm publish`。
3. **有位置参数就会写东西的子命令，要求其余全部是选项。** `git branch` 只读，
   `git branch newname` 会**创建分支**。

> 两个实测踩出来的洞，都留了回归测试：
> - `branch`/`tag`/`remote` 只放进了「要求参数全是选项」那张表，**忘了放进子命令白名单** ——
>   于是它们先被白名单拒掉，那条规则根本没机会生效。
> - `--output=leak.txt` 是**一个** token，按整串比对黑名单只能匹配到 `--output` ——
>   于是所有 `--flag=值` 形式的危险选项全部漏过去。最典型的一类过滤器漏洞：
>   **检查的是名字，喂进来的却是名字加值。**

已知的残余风险写在 `read-only.ts` 的文件头：它认的是**命令文本**不是行为，
PATH 上放一个假的 `git.exe` 它看不出来 —— 那是沙箱该管的事，这一层不管。

## 三个模式

| 模式 | 文件写 | 命令执行 | 命令默认 |
|---|---|---|---|
| `read-only` | 禁止 | 禁止 | — |
| `workspace-write` | 仅工作区 | 允许 | `ask` |
| `full-access` | 任意 | 允许 | `allow` |

**命令执行刻意只有两档。** 「执行大部分命令」在技术上不可定义——你没有办法实现一个「大部分」：按命令名匹配等于没有（`node` 能做任何事），按参数模式匹配又回到不可定义。所以要么不允许，要么允许，中间那一档不存在。

## 三个熔断器

**它们剥夺 allow 规则的批准权，但不强制拒绝。** 这是 Claude Code 的设计，动机写得很直白：**防的是模型出错**。

**① 保护路径** —— `.git`、`.npmrc`、`.mcp.json`、`.bashrc`、`.envrc` 等。它们能改变之后**所有**命令的行为，一旦被改，接下来发生什么就说不清了。

```
判定  ask
原因  protected-path
说明  「.npmrc」是保护路径：allow 规则无权预批准，需要人工确认
⚠ 熔断器剥夺了 allow 规则的批准权
```

**② 关键路径删除** —— 文件系统根 / 家目录 / 工作区及其祖先。

**③ 无法解析的删除目标** —— 这一条是刻意加的，因为 `rm -rf $HOME` 里的 `$HOME` **不像路径**，靠「像不像路径」去筛会直接漏掉。立场取自 doover：**无法静态解析就按危险处理，绝不假设安全。**

```
判定  ask
原因  unresolvable-delete-target
说明  删除目标里有无法静态解析的部分（$HOME）：解析不了就按危险处理
```

## 危险替换与管道

`$()`、反引号、`${}`、进程替换、以及 `curl … | sh` 这类管道直通解释器，都会剥夺 allow 规则的批准权。

**而且不能靠显式 `bash -c` 绕过**——直接给 `args` 不等于不经 shell：

```ts
// 这条会命中守护：
{ command: 'bash', args: ['-c', 'echo $(whoami)'] }
// 这条不会（参数是字面量，shell 不会碰它）：
{ command: 'git', args: ['log', '--grep', '$(literal)'] }
```

> 顺带一提：**我们工具的签名 `{command, args}` 默认不经 shell**，所以那三个 CVE 的整个漏洞类别在我们这里的默认路径上不存在。上面这个守护是为了堵住「显式调用 shell」这唯一的出口。

## 抗疲劳熔断

**确认疲劳有厂商自己的数字。** Cursor 公告原文：

> **「经过足够多次重复提示后，人就不再仔细读了，审批流程也就失去了意义。」**

分类器只拦 ~4% 的动作；只有 ~7% 的会话出现 ≥1 次打断；某些企业客户**之前 ~40% 的动作被拦**。

这里照 Claude Code 的阈值：**连续 3 次或累计 20 次被拦 → 暂停自动放行**，之后一律降级为询问。

**读操作不受影响。** 熔断触发后连看一眼文件都要点确认，那不是更安全，那是瘫痪。

### 它是一道**单向门**，所以必须可见 + 可复位

命中之后，**只有人明确调用 `reset_fatigue` 才会解除**。放行**不会**自动解除 —— 这是刻意的：熔断器命中的前提就是「人在连续打回」，此刻的「允许」正是我们不再信任的那个动作。如果放行能自动解除，它一命中就会被下一次点击关掉，等于没有这个熔断器。

代价是它成了一道单向门，而**没有出口的锁只会训练人去绕过它**（唯一的绕行方式是重启进程，那反而把整套记账一起清掉了）。所以这两件事是熔断器的组成部分，不是附加功能：

- **可见**：命中时发一条 `fatigue_paused` 通知（只说一次，不是每次被拦都发），投影里带 `fatigue: { active, consecutive, total }`。不解释的话，用户只会觉得这个软件突然变得很烦，然后去点更多次「允许」—— 恰好是熔断器想阻止的事。
- **可复位**：`{type:'reset_fatigue', sessionId}`，成功与「本来就没命中」如实区分 —— 报成功会让用户下次真被熔断时不信这个按钮。

⚠️ **「连续」要求两个方向都记账。** 只在被拦时 +1 会让「连续 3 次」退化成「累计 3 次」：两次被拦之间放过的正事全都不作数。而「偶尔被拦一下、中间干了一堆正事」和「连着三次撞墙」是两种完全不同的信号。所以自动放行的路径上也调 `observe('allowed')`。

⚠️ **熔断状态不落盘。** 重启进程就没了。这一条记在这里而不是当成漏洞：重启是用户的明确动作，和点「恢复自动放行」是同一种性质的注意力投入。真要做的话是把它写进检查点，但那会让「重启一下就干净了」变成「重启也不管用」，未必更好。

## fail-closed 的三处

1. **headless 下 `ask` 立即变成 `deny`**，而不是假装问过了。服务端 / `-p` / SDK 这类无人值守场景必须传 `interactive: false`。
2. **默认允许列表是空的。** Cursor 官方示例把 `npm` 整条放进去，而它的匹配是命令字符串前缀——那一条覆盖了 `npm install`、`npm publish` 和**所有 postinstall 脚本**。我们不带这种出厂默认。
3. **规则冲突时 deny 优先**，具体程度不改变决策类别。allow 规则**不能**从 ask / deny 里挖出例外——想要这种能力必须显式切到 `precedence: 'most-specific'`，风险自负。

## 已知边界

**这一层是启发式，不是解析器。** 真正的做法是用 bash 解析器（doover 就是这么做的）并把无法解析的命令整档按危险处理。我们只做启发式，因此：

- **抓得住**：显式关键路径、工作区外路径、`$VAR` / `~` 形式的删除目标、显式替换语法
- **抓不住**：把路径藏进不经 shell 的解释器字符串，且不含可识别删除动词的情况

缓解是结构性的：`workspace-write` 下命令本来就默认 `ask`，所以熔断器只需要在 `full-access` 下承担重量——而那一档本来就意味着高风险。

**还有一条必须写在最前面**：模式切换只能由人侧调用。规则是**模型可以主动降权，但只能请求提权、不能设置提权**。如果存在一个模型可调的提权通道，整个权限层归零。

# 上下文层

## 压缩是一次状态转换，不是一个提示

这是这一层**唯一容易出错、而且出错后极难定位**的地方。

我们立过一条铁律：日志必须能重建出与当时**逐字相同**的消息数组。而压缩会改变消息数组——所以它**不能只是内存里的动作**。

于是 `context_compacted` 事件携带**压缩后的完整数组**，`rebuildMessages` 遇到它**整体替换**。

> **刻意不做增量推导**（「重放时再算一遍压缩」）。那要求重建方也实现一遍压缩算法，两边一旦不一致就是**静默的历史分叉**——而这种 bug 只在 resume 之后才现形。

完整数组让日志变大，但**日志里允许有冗余，不允许有歧义**。

有一条测试专门钉住它：跑两轮（过程中确实发生压缩），然后用全新 Session 从同一份日志恢复，断言两份数组 `deepEqual`。

## 触发条件：即将超出，而不是「有点大了」

压缩是**有损的**，所以它不该是个常备动作，只该在**真的快装不下时**发生。由此推出两条：

**① 预算必须从模型真实的上下文窗口推导，不能是写死的常量。**

我第一版写死了 `96k`。那个数字对任何具体模型都是错的：

| | 写死 96k 的后果 |
|---|---|
| 32k 窗口的模型 | **还没触发就已经爆了** |
| 1M 窗口的模型 | 好端端地就开始丢历史 |

现在是 `可用预算 = 窗口 − 输出预留`，触发线 = 可用预算的 **90%**。

**② 窗口：先探测，探不到才让你声明，最后才是保守默认。**

`GET /v1/models` 是 OpenAI 兼容端点的标准端点，**但大多数情况下它只返回 id**：

```json
{ "object": "list", "data": [{ "id": "deepseek-chat", "object": "model", "owned_by": "deepseek" }] }
```

上下文长度**不在里面**。不过有几家确实给，给了就比猜准：

| 来源 | 字段 | 谁会返回 |
|---|---|---|
| `GET /v1/models` | `max_model_len` | vLLM |
| `GET /v1/models` | `context_length` | OpenRouter 等网关 |
| `POST /api/show` | `model_info.<arch>.context_length` | **Ollama** |
| `GET /props` | `n_ctx` | llama.cpp |

所以启动时**挨个试**，优先级是：

```
用户声明（--context-window / MVS_CONTEXT_WINDOW）  >  探测  >  内置模型表  >  保守默认（32k）
```

**关键是「探到就如实说来源，探不到就明说探不到」**：

```
上下文    窗口 32768 · 可用预算 28672（预留 4096 给输出）
          来源：保守默认 —— /v1/models：只返回了 id、object、owned_by，没有上下文长度；
                            /api/show：fetch failed；/props：fetch failed
```

**绝不因为探测失败就假装知道，也绝不因为探测成功就当成权威。** 探到的值也标来源，你能一眼看出它是「查到的」还是「你声明的」。

> 实现细节：探测「端点通了、但返回里没有这个字段」也**必须留下说明**。我第一版只收集抛出来的异常，结果最常见的那种情况完全没有诊断——用户看到一串 404 会以为端点不通，实际是端点通、只是那家不给窗口。

**③ 估算本身会自我校准 —— 这比拿到窗口更有用。**

窗口只是**分母**，我们真正需要的是**分子准不准**。估算要是偏了 2 倍，任何窗口大小下判断都是错的；而窗口值你至少能声明，估算的误差没有任何配置项能修。

好消息是**真实值每次调用都有**：`usage.prompt_tokens` 就是这次请求真实的输入 token 数。拿它去除我们自己的估算得到一个系数，乘回后续估算上——**估算就会收敛到那家模型真实的分词器，而我们并不需要分词器本身**。

三条纪律：

- **`actual <= 0` 的样本直接拒收**（很多端点不给 usage，不能让它把系数带成 0）
- **单次比值钳制在 `[0.4, 3]`**，第一个样本直接采用、之后走指数滑动平均（α=0.3）
- 口径必须对齐：估算里**要含工具 schema**，因为端点的 `prompt_tokens` 是把 schema 算进去的

宁可慢一点收敛，也不要被一个野点带跑。

## 两级策略，先便宜后贵

**① 裁剪超大工具结果** —— 无模型调用、确定性、随时可做。

一个 `npm install` 的输出就能吃掉几万 token，而头尾几 KB 通常就够了。阈值取自本机运行的 DSH 的 `compaction-tool-result-pruner` 配置（`8192 / 4096 / 1024`）—— 这几个数字是被实际跑过的。

**② 丢弃最老的轮次** —— 仍然超预算时的兜底，**留下显式标记**。

```
[上下文压缩] 已省略更早的 7 轮对话（28 条消息）。它们不在当前上下文里，
但完整记录仍在事件日志中。如果用户提到更早的内容，直接说不记得，不要编造。
```

让模型知道「这里有一段被省略」，比让它以为对话本来就始于此处要好。

**刻意不做「让模型总结历史」**：那需要一次额外调用、引入不确定性，而且总结本身可能是有损且不可复现的。先做确定性的两级；真需要总结再加。

## 两条不能违反的约束

1. **工具调用与结果必须成对** —— 丢掉 assistant 的 `toolCalls` 却留下 `tool` 结果（或反过来），接口会直接报错。所以**只能在轮次边界上切**。有专门的测试断言两边的 id 集合完全相等。
2. **最近的轮次永远不动** —— 压缩的是历史，不是当下正在处理的上下文。系统提示同理，永不动。

## 实测效果

```
压缩前   41 条消息 · 75154 估算 token · 最长一条 26028 字符
压缩后   14 条消息 ·  4932 估算 token           （省下 70222）
不变量   系统提示原样 ✔  工具调用成对 ✔  标记只有一条 ✔  保留最近 3 轮 ✔
```

## token 估算是估算，不是分词

真分词需要 tokenizer（一个几百 KB 的数据文件加一份分词实现）。估算是按字符分类加权的：**ASCII 约 4 字符 1 token，CJK 约 1 字符 1 token**，并且**误差方向偏保守（宁可高估）**。

> 这里原本写的是「tokenizer 在 npm 包里，这个环境装不上」。**那句话是错的** —— npm 在开发机上是通的（走 npmmirror 镜像）。所以真分词**可以**加，它是一个尚未做的选择，不是被环境堵死的路。之所以先不加：估算的用途只有一个（判断该不该压缩），而它已经被真实 `usage.prompt_tokens` 校准到各家分词器上了（见 `src/context/calibration.ts`）；引入 tokenizer 会把一份第三方数据文件带进一个需要长期演进的判定路径。

**用途只有一个：判断「离撑爆还有多远」。** 用来算钱精度不够，用来决定「该不该压缩」足够了。

## 已知边界

- **如果受保护的最近几轮本身就超预算，压缩救不了。** 此时会发一条 `context_over_budget` 通知，**但不拒绝调用**——我们的估算偏保守，真正说了算的是模型服务端，不该拿一个启发式挡掉本来能成的请求。每轮只警告一次，否则会变成事件流噪音。
- **窗口探测不是万能的。** OpenAI / DeepSeek / Anthropic 的兼容层**都不返回**上下文长度，只有 vLLM / OpenRouter / Ollama / llama.cpp 这类会给。探不到就退回声明或保守默认，并且**如实标出来源**。
- **窗口是声明或探测来的，不是权威。** 声明错了会在两个方向上出错：猜大了运行时报错，猜小了无谓地丢历史。我们只能把默认值取保守、把来源打出来。
- **估算是估算，不是分词。** 但它会随每次调用的真实 `usage` **自我校准**，所以误差会收敛。校准状态在投影的 `contextCalibration` 里，UI 可以显示。
- **压缩是有损的，但不是不可逆的。** 被裁掉的原文仍完整保存在 `events.jsonl` 的 `tool_settled.content` 里；文件内容还能用恢复工具还原。**需要细节时重新读取，比依赖记忆更可靠**——这句话我写进了给模型的裁剪提示里。
- **token 估算是估算，不是分词**（见上）。

# 传输层

## 这里新开了一个能执行命令的端口

我们前面花了大量篇幅讨论「怎么让 agent 不越界」。**如果在这里开一个谁都能连的端口，前面那些讨论就被一次性绕过了。** 所以四道防护全部默认开启，且各有一条独立的测试专门证伪它：

| 防护 | 挡什么 | 实测 |
|---|---|---|
| **只绑 `127.0.0.1`** | 局域网访问 | ✅ 打印出的地址必是回环 |
| **必须带令牌** | 同机其他进程 | ✅ 无令牌/错令牌 → 401，用 `timingSafeEqual` 比较 |
| **校验 `Host` 必须是回环** | **DNS rebinding** | ✅ 伪造 `Host: evil.example.com` → 403 |
| **校验 `Origin` 必须是回环** | 恶意网页发起的跨站请求 | ✅ `Origin: https://evil.example.com` → 403 |

**第 3 条最容易被忽略。** 攻击者让自己的域名解析到 `127.0.0.1`，再诱导用户的浏览器去访问它——请求确实打在回环地址上，但 `Host` 头是攻击者的域名。**只检查「是不是来自本地」是不够的，必须检查 `Host` 本身。**

而且**升级请求（WebSocket）走完全相同的鉴权**。很多人只给 HTTP 路由加了鉴权、忘了 upgrade 那条路——那是最容易漏的一道门。

实测输出：

```
① 无令牌               → HTTP 401
② 伪造 Host            → HTTP 403  Host「evil.example.com」不是回环地址。这类请求可能来自 DNS rebinding，已拒绝。
③ 恶意 Origin          → HTTP 403  Origin「https://evil.example.com」不被允许
④ 正常请求             → HTTP 200  {"ok":true,"session":"main"}
⑥ 开发页（无令牌）     → HTTP 401   ← 开发页没有特权
```

## 端点

| | |
|---|---|
| `GET /` | 开发页（需 `?token=`） |
| `GET /health` | 存活检查（也需令牌） |
| `GET /state` | 整份索引：工作区 + 会话摘要 + 打码后的配置 |
| `GET /projection?sessionId=` | 某个会话的快照（迟到加入时读） |
| `GET /transactions?sessionId=` | 该工作区可撤销的改动列表 |
| `POST /command` | 发命令 |
| `GET /ws?token=…` | WebSocket 事件流 |

**下行帧有三种**：

| | |
|---|---|
| `{kind:'state'}` | 整份索引。**连上第一帧就是它** —— 侧栏靠它立刻画出工作区树和「谁在等我」的徽标 |
| `{kind:'projection'}` | 某个会话的完整快照，**声明在看它之后才给** |
| `{kind:'event', envelope}` | 之后的增量。信封带 `sessionId`，多会话下才知道是谁在说话 |

索引整体推、会话内容增量推，这个不对称是刻意的：索引小且变化少，而 token 级的
逐字流是高频的 —— **只推正在看的那些会话**。没有这道裁剪，每开一个标签页都会
收到所有会话的逐字流。

**`watch` 必须走 WebSocket**（`{type:'watch', sessionIds:[…]}`）。它声明的是
「**这条连接**在看哪个会话」，一次性的 HTTP 请求没有可归属的连接 —— 服务器会
明确拒绝这种用法，而不是假装成功（假装成功会让调用方一直等一个不会来的投影）。

## 撤销走传输层

恢复层（`recovery restore`）早就有了，但那是本机 CLI。**撤销要在客户端可用，
就得有一条命令**，于是有 `{type:'revert', sessionId, txnId, force?}`。

这里有两个容易做错的地方：

- **撤销的结论不等于命令的成败。**「文件之后被改过，所以我没动它」是一条正常
  结果：命令成功了，撤销被拒绝了。混成一个 `ok` 会让界面显示「撤销成功」而
  文件根本没变，所以 `ok` 如实转达恢复层的结论。
- **投影要带上每次工具调用的撤销状态**（`toolCalls`）。不带的后果是刷新之后
  撤销按钮消失 —— 而「我能不能撤掉刚才那一步」不该取决于这个标签页开了多久。
  注意 `messages` 里只有 `content`（回填给模型的原文），**没有 ok 和 summary**，
  所以卡片状态另开一张表，不从消息推。

撤销状态表还带着一个小状态机：撤销事务 `T` 会**新建**事务 `R`（恢复本身也必须
可恢复），所以要重做就得去撤销 `R`。字段叫 `undoTxnId` 而不是「原始事务 id」，
就是因为它会在 `T`、`R`、`R2`… 之间来回换。

有一条规则特别容易漏：**撤销部分成功时不算翻转**。恢复层可能有的文件恢复了、
有的因冲突跳过了，此时文件停在中间状态 —— 标成「已撤销（可重做）」就是按了
一个说谎的按钮。`test/projection.test.ts` 专门钉住了这一条。

## 一个关键决定：`user_message` 立刻返回

**HTTP 响应不等待整轮跑完。** 一轮可能跑几分钟，中途还会停下来等人审批——让响应挂在那里会把客户端也一起挂住。进度全部走事件流。

有一条测试专门钉住它：跑一轮 50 段的回复，断言 `POST /command` 在 200ms 内返回。

## 自己实现的最小 WebSocket

Node 没有内置 WS 服务端，而**守护进程刻意保持零运行时依赖**。这个决定和「npm 装不装得上」无关 —— npm 在开发机上是通的：一个要执行命令、要碰用户文件的进程，**发货时不带 `node_modules`** 是真实的安全收益（没有传递依赖、没有 postinstall 脚本、没有供应链更新面）。所以手写了 RFC 6455 的服务端部分——只需要文本帧、关闭、ping/pong。

> ⚠️ 前端是另一回事，见文末「尚未构建」：Vue + Vite 是**构建期**依赖，产物是静态文件，守护进程的运行时依赖仍然是零。

两处规范要求不能省，都写在代码注释里：**客户端发来的帧必须带掩码**（没带是协议错误），**服务端发出的帧必须不带掩码**（带了浏览器直接断开）。

用 Node 内置的 `WebSocket` 客户端做了端到端验证，互通。

## 开发页是什么、不是什么

**它不是产品 UI。** 它是一张**体检表**：能连上就说传输通了，能收到事件就说事件流通了，能点「允许」就说审批通道通了。

写成一页零依赖的 HTML，是为了不让人为了「看一眼效果」先去装一堆东西。产品客户端走**同一份协议**，但会是构建产物（框架与构建工具见文末「尚未构建」）。

# 运行时

## 架构：host 与客户端的边界

**运行时是独立于 UI 的一侧。** 这条边界的确立理由很直接：桌面用户一定会关窗口，而关窗口不该丢掉正在等审批的任务。

```
src/protocol/   跨边界的契约（事件、命令、投影、检查点）
src/host/       运行时：会话、循环、事件、检查点、传输
src/web/        UI（零构建，尚未开始；目前只有 client 状态核心 store.js）
```

**纪律：客户端不持有任何权限。** 它只渲染投影、回答提示。所有判定都在 host。

> 这个划分取自本机运行的 DSH：它的 host 组合「保留了一切 preset 不该拥有的东西：注册表本身、沙箱与审批栈、持久化、以及模型路由」。组件边界按**所有权**划，不是按传输方式划。

## 一次工具调用的完整顺序（顺序就是设计）

```
policy_decision      策略判定：放行 / 拒绝 / 问人
  （若是 ask）
approval_requested   广播请求（**先注册应答通道，再广播**）
approval_resolved    人回答了
tool_intent          落盘：我打算执行了
  ...执行...          ← 死在这里 = 有 intent 无 settled = 状态未知
tool_settled         落盘：结果 + 恢复事务 id
```

三个顺序各有理由，而且都是实测踩出来的：

- **intent 必须先于执行** —— 否则区分不出「从没开始」和「开始了但结果丢了」。
- **intent 必须在审批之后** —— 否则「等人回答时崩溃」会被误报成「状态未知」，而实际上什么都没执行，白让人紧张一次。
- **应答通道必须先于广播** —— 反过来的话，一个反应很快的客户端会在「事件已到达」和「会话已准备好接受回答」之间那几毫秒里拿到「未知的审批 id」。**那正是「UI 提供了操作但点了没用」的形态**（Claude Code #34368 就是这个病）。开发时这个 bug 被测试直接抓到了。

## 恢复时不猜

启动时扫描未结算的工具调用：

| 情况 | 处理 |
|---|---|
| 有 intent、无 settled | **状态未知** → 标成 `interrupted`，拒绝继续，交给人 |
| 有审批请求、无结论 | 什么都没执行（intent 在审批之后）→ 重新问一次即可 |
| 检查点条数 > 日志条数 | 日志被截断过 → **报警**，不照常恢复 |

**不提供「就当它执行过了」这个选项。** 那需要人判断副作用是否已发生，而不是运行时代替人判断。真跑了一半的情况有恢复层的快照兜底。

> 两件事合起来才有意义：**日志保证你知道「可能发生过」，恢复保证你「能撤掉」。缺任何一半，剩下那半都是假的。**

## 两个文件，两种写入模式

| 文件 | 内容 | 写法 |
|---|---|---|
| `events.jsonl` | 追加的事件流，含完整消息 | **只追加**，线性增长 |
| `checkpoint.json` | 状态：轮次、步数、待办、中断标记 | 每步**原子重写**，大小恒定 |

**为什么不把消息放进检查点**：那会变成 O(n²)——每步全量重写整个对话历史。1000 步、1MB 历史就是 1GB 写入，而且这个坑只在长任务上暴露，也就是在用户那里。检查点只记「日志看到第几条」。

**原子写是必须的**：临时文件 → `fsync` → `rename`。直接覆写的话，崩溃正好发生在写的中间，检查点就是半个 JSON——那比没有检查点更糟，你会以为状态损坏了，实际它只是不确定的。

**流式 token 增量不落盘**：一天能撑到几个 GB，而恢复时一点用都没有（最终消息已完整存在于 `assistant_message`）。实测：12 条事件、1783 字节，日志里零个 token 级事件。

## 事件日志必须能重建出逐字相同的上下文

所以日志里存的是**完整内容**而不是摘要：

- `assistant_message` 带完整 `toolCalls`，不是一个数量
- `tool_settled` 带回填给模型的 `content` 原文

**日志里允许有冗余，不允许有歧义。** 有一条专门的测试钉住它：跑完一轮后用全新 Session 从同一份日志恢复，断言两份消息数组 `deepEqual`。

## 刻意不做：事件溯源

需要区分两件事：

| | trace / 可观测 | 事件溯源 |
|---|---|---|
| 是什么 | 追加记录「发生了什么」 | 日志是**真相来源**，内存状态是它的投影 |
| UI 迟到加入 | 拿快照 + 订阅 | 重放日志 |

**UI 需要的是「状态可重建」，不等于「执行可恢复」。** 前者便宜，后者贵。我们用「发事件 + 落检查点 + 快照投影」满足全部 UI 需求，不需要让日志当真相来源。

**但纪律是现在就要立的**：所有状态变更走**单一转换函数**并发射事件。这条几乎零成本，而且它把事件溯源永久保留为选项——因为它只是把这个发射器升级成真相来源，不用改别的。真正要避免的是「到处就地 mutate 状态对象」，那才是改不动的。

### 产品 UI

**设计系统完全按 DSH 来做。** 不是「照着感觉像」，而是可复核地照搬：

| 层 | 来源 | 落地方式 |
|---|---|---|
| 颜色 / 字体 / 圆角 / 阴影 | DSH 主题包 `@deepseek-ai/dsh-client-ui-theme` | `tools/extract-dsh-tokens.mjs` 自动提取 → `src/web/tokens.css`（浅色 422 个 + 深色 204 个覆盖） |
| 结构尺寸 | DSH 各 UI 包的实测值 | `style.css` 顶部的 `--dsh-*` 层（内容列 920px、消息间距 12px、输入区 dock inset 8px、滚动条 5px…） |
| 组件外观 | 对应组件的 CSS module | `tools/dsh-css.mjs` 转储后照抄（审批卡、侧栏、输入区、权限选择器…） |

```bash
node tools/extract-dsh-tokens.mjs   # 重新提取设计 token（升级 DSH 后跑）
node tools/dsh-css.mjs approval     # 转储某个 DSH 包的组件样式，用于对照
npm run web:build                   # 构建前端产物到 dist/web
npm run serve                       # 守护进程把它当静态文件吐出去
```

`--app` 会用 Edge 的应用窗口打开界面（无地址栏、独立 profile、Windows 自带所以零安装）。
开发时用 `npm run web:dev`（Vite，带热更新），它把 API/WS 代理到守护进程。

**主题：浅色 / 深色 / 跟随系统**，和 DSH 的三个选项一致，用同一套属性名
（`body[data-ds-dark-theme]`）所以能对着它的样式互相调试。
首屏由 `index.html` 里一段内联脚本在解析 HTML 时就打上属性 —— 不等 bundle，
否则深色用户会先看到一帧白色。切换是纯本地的，不进协议：换个配色不该产生审计事件。

**抄下来最值钱的一条**：DSH 的描边是 `.5px` 而不是 `1px`（外壳分隔线、行分隔线都是）。
半透明描边在 1px 下会显得脏而重 —— 这是自己调总觉得「差一点」的常见原因。

已实现：左侧栏（工作区 › 会话嵌套、状态在最左一列、选中灰底、折叠时告警上浮、
**宽度可拖**）、时间线（工具卡为主、文字为旁白、内容列限宽 920px 居中）、
**撤销/重做按钮**、审批卡（DSH 的「警示色带 + 正文 + 右对齐操作行」结构）、
熔断提示条与复位按钮、上下文用量与**窗口来源**、添加工作区（含后果说明）、
输入与中断、断线自动重连并重拉。

**左下角是设置**（DSH 的 `.footArea > .settingsArea` 就在那儿），**添加工作区在头部**
（对应 DSH 的 newSession 图标按钮）—— 这两处位置是照 DSH 的 logoRow / footArea 分的，
不是我挑的。

设置面板只放两类字段：**能改的**（模型端点/模型名/密钥、新会话默认权限、压缩触发比例）
和**只读但排查问题必须有的**（配置文件路径、数据目录、密钥来源、明文警告）。
中间那类「能看见但改了没用」的字段一个都没有 —— 让用户改完发现没生效比不放它更伤人。
保存时**只发改动过的字段**：整份回传会把界面没显示的字段以默认值写回磁盘，
用户没碰过的东西被悄悄改掉，而且看不出来。

密钥那一栏把**两件事分开说**：「我的 key 从哪来」（环境变量名）和「它是不是明文躺在磁盘上」。
只给一个打码字符串的话，用户没法判断自己该不该去改。打码值原样回传表示「没改密钥」，
所以用户改个模型名不会被逼着重新粘贴一次 key。

界面底部是**状态栏**：权限模式、后台作业计数、上下文用量、连接状态。

权限模式放在那里而不是标题栏：它们是**关于当前会话怎么跑**的参数，和「你在哪个工作区、
哪个会话」是两类信息。挤在标题栏里的后果实测过 —— 标题被压成了 34px 宽的竖条。

权限选择器按 DSH 的 `permission-presets` 做：**无边框**的 28px 行内按钮 + 上弹菜单
（我第一版用的是带边框的原生 `<select>`，那是自造外观）。代价是键盘和 `aria` 必须
自己做对 —— `aria-activedescendant`、↑↓/Home/End/Enter/Esc、点击外部关闭都实现在
`Dropdown.vue` 里。这类缺陷在自己用鼠标点的时候**永远测不出来**。
⚠️ 它**只能是给人用的** —— 模型可以请求降权，但提权必须由人点这里；
如果存在一个模型可调的提权通道，整个权限层就归零了。

输入框是**悬浮**的，不贴底：通栏那条线会把内容区切成一截一截的，而实际关系是消息从下面
滚过去、输入框浮在上面。两个容易做错的点：外层的 `pointer-events` 必须是 `none`（否则
渐变区会吃掉点击，用户选不中下面的文字），以及时间线的底部留白要依据**实测的**输入区
高度（`--dsh-composer-height`）—— DSH 自己就是
`calc(var(--dsh-composer-height, 152px) + 16px)`，写死一个数字必然在长输入时露馅。

v1 刻意没做（都不是遗漏，是排期）：

- **markdown 渲染**。助手正文现在按**原文**显示（`white-space: pre-wrap`）。
  这与「直接输出 markdown 原文」一致，也省掉了渲染器的注入面 —— 渲染时必须构造
  DOM 节点、绝不拼 HTML，因为模型输出和文件内容都是不可信输入。
- **设置面板**。模型 / 密钥 / 窗口 / 模式目前只能走 CLI（`npm run config`）。
- **审批卡的其他选项**。协议里 `approve` 只有一个 `granted: boolean`，
  没有携带规则的能力，所以「本次会话都允许」和「永久规则」**画都没画** ——
  画一个点了没用的按钮比少一个按钮更糟。

界面结构上仍然遵守早先定下的规矩：

- **侧栏在最左**，**会话嵌在工作区下面**（一个会话改了哪些文件取决于它在哪个目录里跑，
  把会话平铺成列表就等于把这个信息藏起来了 —— 而这正是用户按「撤销」时需要知道的事）。
- **状态显示在行的左边**，形成一列可以竖着扫。**选中用灰底**，颜色只留给状态。
- 折叠的工作区把子会话的告警**上浮**（等确认 > 中断未结算 > 正在跑）。
- 界面里不用盾牌和锁的图标。

### 前端：可以用框架，而且有一个**决定性**的理由

⚠️ **先纠正一个我写错的前提。** 这一节原本写着「npm 在这个环境不通，所以客户端必须零构建」。
**那是错的** —— 我把「默认源 `registry.npmjs.org` 不通」当成了「装不了包」。开发机的 npm
配的是 **`registry.npmmirror.com`（国内镜像）**，实测可达，`npm ping` 返回 PONG，
Vue 3.5.43 / React 19.3.0 / Svelte 5.57.1 / Vite 8.3.2 都查得到，`devDependencies`
（TypeScript、@types/node）也已经装好了。

前提一变，框架问题的性质就变了：**有了构建步骤，客户端可以直接 import 服务端的协议模块。**

实测确认过：`src/protocol/types.ts` 与 `src/protocol/projection.ts` 的**整个依赖图都是
`import type`**，没有一处 `node:` 运行时导入。所以浏览器打包器可以安全地引入它们 ——
包括其中的运行时纯函数：

| 客户端可以直接用 | 于是不必再 |
|---|---|
| `HostEvent` / `ClientCommand` / `SessionProjection` 等类型 | 在客户端用 JSDoc 重新声明一遍协议 |
| `alertOf` / `worstAlert` / `EPHEMERAL_EVENTS` | 手抄一份状态→告警的映射 |
| `foldToolCall` / `rebuildMessages` / `findUnsettledCall` | **重写一遍折叠逻辑并祈祷它和服务端一致** |

最后一行是关键。零构建方案下，客户端只能把折叠逻辑再实现一遍，而我在
`src/web/js/store.js` 的注释里把那条路的风险写得很直白：「两份实现不一致的后果是
**一直在线的界面和刚刷新的界面显示不同的东西**」。**这个风险现在可以整条消掉** ——
前提是选一个能编译的框架。这一条比框架之间的任何差异都重要。

#### 三个候选（都实测可装）

| | 流式那一处 | 和现有 store 的贴合度 | 其他 |
|---|---|---|---|
| **Vue 3.5** | 细粒度依赖追踪：`{{ text }}` 只重渲染那个节点 | **最高**：`reactive(store)` 直接包住我们已经在用的可变普通对象，`store.js` 一行都不用改 | 官方中文文档是第一等的；国内生态最厚 |
| Svelte 5.57 | runes，同样细粒度 | 中等：要改成 `.svelte.js` 并用 `$state` 包一层 | 产物最小，但没有虚拟 DOM 的调试体验更依赖编译期 |
| React 19.3 | 需要把流式文本单独拆组件 + `useSyncExternalStore` | **最低**：我们的 store 就地 mutate 且没有通知机制，得额外加一套 subscribe/notify | 生态最大，但这个应用用不到那么多 |

**已定：Vue 3 + Vite + TypeScript。** 决定性的不是语法偏好，是**它和已经写好的那份纯状态核心零冲突**
—— 其余两个都要给 store 加一层适配（Svelte 改写法、React 加订阅），而适配层正是将来会和服务端漂移的地方。
Vue 的官方中文文档与国内生态厚度是额外的长期收益。

#### 目录：**一个 package，两个 tsconfig** —— 不是两个项目

这一条一开始我想错了，记下来免得再走一遍：我建议过把前端拆成独立子项目 `web/`，理由是
「让内核的零依赖叙事干净」。**那个理由不成立** —— Vue/Vite 放哪个 `package.json` 里都只是
`devDependencies`，守护进程发货时一样不带 `node_modules`。**零运行时依赖这条属性跟 package
边界无关**，拆分只换来两个 `npm install` 和两份要同步的路径映射。

所以：**同一个 package.json、同一个 `npm install`、代码都放 `src/` 下。**

但**必须有两份 tsconfig** —— 这不是"两个项目"的仪式，是两边的编译环境真的不同，而且
合并会造成实际的安全损失：

| | 服务端（现有 `tsconfig.json`） | 前端（新增 `tsconfig.web.json`） |
|---|---|---|
| `lib` | `["ES2023"]` —— **没有 DOM** | `["ES2023", "DOM"]` |
| `module` / 解析 | `nodenext` | `bundler` |
| 补充 | `erasableSyntaxOnly`、`allowImportingTsExtensions` | Vue SFC 支持 |

**`lib` 必须分开，这条最要紧**：如果服务端也带上 `DOM`，那么有人在 `src/host/` 里写了
`document.title = …`，类型检查会**通过**，而它到运行时才炸。给服务端一个没有 DOM 的 `lib`，
是让类型系统替我们守住那条边界。

落地方式：根 `tsconfig.json` 加 `"exclude": ["src/web"]`，新增的 `tsconfig.web.json` 里
`"include": ["src/web"]`，`npm run typecheck` 两条都跑。共享的 `src/protocol/*.ts` 必须同时
通过两份配置 —— 它们只用 `import type` 和普通语法，满足得了。

> ⚠️ 注意 `foldToolCall` / `alertOf` 这些是**运行时值**，不是类型：`import type` 会被完全擦除，
> 而这些真的会进打包产物。它们能进浏览器，是因为那两份文件的依赖图**全是 `import type`**
> （已实测）。将来往 `src/protocol/` 里加运行时依赖时要意识到这一点 —— 那会同时影响服务端和浏览器。

#### 构建与运行的分工

- **构建期**：Vue + Vite 是 `devDependencies`，产物是静态文件。
- **运行期**：守护进程的运行时依赖**仍然是零** —— 它只把 `dist/` 当静态文件吐出去。
  这条不因为引入前端框架而改变，而它是有价值的：一个要执行命令的进程，发货时不带
  `node_modules` 意味着没有传递依赖、没有 postinstall 脚本。
- 代价：**做前端需要先 `npm install`**（README 开头的「不需要 npm install」只覆盖跑内核和跑测试）。

**开发期的 HMR 已经不需要额外条件**：Vite 开发服务器（`127.0.0.1:5173`）代理 API 与 WS 到守护进程，
而守护进程的 `isLoopbackOrigin` **只看 hostname、不看端口**，所以那个 Origin 现在就能通过 ——
不必为了开发放松那道防护。

#### 架构：已定（2026-02 讨论）

**交付形态 —— Edge `--app=` 应用窗口。** 已实测的三个前提：Edge 149 随 Windows
自带、WebView2 运行时 149 同在、`csc.exe`（.NET Framework 4.0）在。所以
**不需要任何原生代码就能有独立窗口**，而且验证过 `--user-data-dir` 能在独立目录
建出完整 profile（`Default` / `Crashpad` / …），**不碰用户自己的 Edge 数据**。

选它的理由是它和「浏览器标签页」共用同一份前端代码，所以将来要升级到
WebView2 + C# 原生宿主（换取托盘、图标、单实例、窗口状态）时，**前端一行都不用改**
—— 两条路都是 WebView 指向同一个 URL。原生宿主因此留作产品化阶段的可选项，不是前置。

**令牌 —— httpOnly + `SameSite=Strict` cookie**，不再把令牌放在 URL 里
（那会让它进浏览器历史和书签）。

⚠️ 有一个必须记住的坑：**cookie 的作用域是 host 不是 port**。两个 daemon 分别跑在
`127.0.0.1:3090` 和 `127.0.0.1:3091` 会共享 cookie —— 所以 **cookie 名里要带端口**
（形如 `mvs_s_3090`），服务端只认自己那一个。端口是 `listen()` 之后才知道的
（默认用 0 取随机端口），所以 cookie 名得在那之后才算得出来。

**渲染层 —— 无框架 + keyed 增量 + rAF 合并。**
（这一项**已被上面的发现推翻**：既然 npm 通、框架可用，重写折叠逻辑就不再是必须的代价。
以 Vue 3 为准 —— 它把一个抽象层交出去，换回的是和服务端共用同一份折叠逻辑。）

> 原方案的依据仍然成立、只是不再划算：时间线的形状是**追加为主、不重排、只有流式那一个节点
> 在高频变化**，这恰好是手写增量渲染最擅长的场景，真正的性能决定也不是框架而是
> **脏标记 + `requestAnimationFrame` 合并**（没有它，流式输出就是每个 token 一次整树更新）。
> Vue 的调度器已经把这件事做掉了，所以这条不再是需要我们维护的东西。

#### 尚待决定

- **用户怎么启动它。** 固定端口会冲突；随机端口则界面得找得到它。倾向写到
  `~/.mvs-agent/` 下的端口文件 + 一个启动快捷方式，等交付形态落地后再定。

#### 已经确定、不用再讨论的约束

- **协议是边界**，客户端不持有权限，只渲染投影 + 回答提示。
- **状态模型已定并已落地**：`src/protocol/projection.ts` 的折叠规则，**前后端共用同一份**。
- **模型输出永不进 `innerHTML`**：全部走 `textContent`，markdown 也构造成 DOM 节点。
  这条是硬线，不是风格 —— 模型输出和文件内容都是不可信输入。

#### 已经写好的东西现在怎么处理

`src/web/js/store.js` 是零构建方案下的产物：它把「一份投影 + 一串增量事件」折成时间线的
纯函数核心，其中**折叠逻辑是服务端 `foldToolCall` 的第二份实现**，文件注释里专门写了两道
防线来防它和服务端漂移（「必须在同一个漏斗里更新」「seq 断号就重拉投影」）。

既然前端能用 Vue + TS，**这份第二实现应该被删掉**，改成直接 import 服务端的：

```ts
import { foldToolCall, rebuildMessages } from '../../protocol/projection.ts'
```

它仍然有价值的部分是**别的**：断号检测（`gap` → 重拉投影）、以及「什么都不信，重新拉一份
投影覆盖本地」这个抗漂移策略。这些照搬过去，折叠逻辑本身则不再重写。

### 真正的沙箱（最重要的缺口）

这是「**本地执行，但必须有边界**」这条要求里还差的一半。

现在有的是**权限层**：它决定一次调用允许 / 询问 / 拒绝，并且它**不是**沙箱 ——
`run_command` 一旦放行，就在真实环境里以真实权限跑，文件围栏只约束文件工具，
约束不了命令。

调研结论与实测记录都在 `docs/os-sandbox-findings.md` 与
`docs/sandbox-platform-matrix.md`。结论是：Windows 上不需要管理员就能建立的
沙箱（AppContainer）**确定性地无法执行打包进去的 node.exe**；而限制型令牌那
条路，DSH 文档记下的正确做法是保留 **logon SID + Everyone** 在限制列表里，否则
子进程会以 `0xC0000022` 直接死掉。我们用权限层换来的诚实说法是
`enforcement: 'partial'`。

### 事件溯源

刻意不做。日志是 trace，不是真相来源 —— 内存状态才是，日志用来重建它。

⚠️ **一处必须记住的区分**：事件日志记录的是「**工具做了什么**」，而恢复需要的是
「**文件系统变了什么**」。**这两者不等价**——正是这个不等价造成了 Claude Code 与
华为 CodeArts 的同一个洞。所以真正要紧的不是事件日志本身，而是**快照边界**
（何时拍的、覆盖范围、哪些没覆盖），这也是 `context_compacted` 携带完整消息数组、
`tool_settled` 携带完整 `content` 的原因：**日志里允许有冗余，不允许有歧义。**

回放、分支（从第 5 步换条路重跑）、评估、断线重连——这几件事日志已经能支撑了，
缺的只是用到它们的功能。

### 真实端点验证

DeepSeek 的真实端点**从未验证过**：本机网络不通且没有 key。协议形状与 fixture
回放都验过了，但「换一家真实端点」这件事没有证据。Ollama 的窗口探测是实跑验证的。
