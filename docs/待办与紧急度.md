## 一、先更正三个判断（结论变了，不是补充）

### 1. ❌ 不借 Venture 的 delta / WAL 存储引擎

原建议是"把整树快照换成 delta + 内容寻址 + WAL"。**核实后不成立**，两个方向同时否掉：

**（a）`file_history/` 是"减配版 git"，不是新机制。** 按功能对位：blake3 内容寻址 ≈
`.git/objects`、64B 分块 + gear 滚动哈希 ≈ packfile delta、锚点链 ≈ delta chain 深度限制、
WAL + `recover_from_wal` ≈ reflog + `index.lock` 恢复、LRU 配额 ≈ `git gc`、
rollback 的 turn/record/file 级 ≈ `checkout`/`restore`/`reset`。
而 git 真正难的部分（packfile 的 delta 选择启发式、`fsck`、ref 原子更新、index 并发锁）
它一个都没有。**4,133 行的终点是"那不如直接用 git"。**
（它那套"自适应"上一轮已核实是空的：`high_frequency_writes` 无人读取、
`external_edit_count` 恒为 0、`BackupMode::default()` 还是 `Snapshot`。）

**（b）它优化的是我们**已经解决**的那一栏。** 见 `src/recovery/snapshot.ts:103-114`：

```ts
const reuse =
  verify !== true &&
  cached.size === stats.size &&
  cached.mtimeMs === stats.mtimeMs
if (reuse) { … } else { hash = await hashFile(abs) }
```

**未变的文件从来不重读内容**，只做一次 `lstat`；blob 又是内容寻址去重的
（`src/recovery/store.ts:58` → `blobs/<hash[0:2]>/<hash[2:]>`）。

于是真实成本结构是：

| 环节 | 成本 | 谁在承担 |
|---|---|---|
| 读目录 + `stat` | **O(全树文件数) × 2 次/变更** | ← **这才是瓶颈** |
| 哈希 | 只对变了的文件 | 已经很便宜 |
| 存字节 | 内容寻址去重 | **已经是 O(变更字节)**，不是问题 |

delta 引擎优化的是**最后一栏** —— 那一栏我们早就解决了。
**移植它 = 花几千行去优化一个不存在的瓶颈，同时把"快照式"改成"历史式"。**

### 2. ❌ 不做会话级 / 整树回滚

这条是**我们自己的代码否决的**，不是外部意见。见 `src/recovery/guard.ts:65-70`：

> 有后台作业正在跑。它随时可能在任意时刻写文件，所以「动作前 → 动作后」这个时间窗里的
> 归属**根本无法确定**……**宁可让这一段时间里没有撤销可用，也不提供一个会删错东西的撤销。**

会话级整回滚**就是"归属最不确定"的那个粒度** —— 它跨越几十次调用、跨多个并发写入窗口。
**在已有的原则下，它不该存在。** "更大的按钮"也不是用户要的东西。

### 3. ✅ 真正该做的两件（都不是"更强的撤销"）

| 需求 | 需要吗 | 理由 |
|---|---|---|
| 撤销**已跟踪文件**的改动 | ❌ 不需要 | git 已经覆盖（`git diff` / `git checkout --`）。我们在这里是**冗余**的 |
| 撤销**未跟踪文件**的新增/删除 | ✅ 需要 | git 看不见 —— 删除未跟踪文件之后 git 帮不了你 |
| 撤销 **shell 副作用**（`rm`、`sed -i`、构建产物、代码生成） | ✅ **需要，且是唯一的硬差异** | 竞品文档里那个洞就在这（copilot-cli#1675 是反面教材） |
| **看懂这一步改了什么**（diff） | ✅ **最高频** | 撤销是事后补救，一年用几次；确认改了什么，一小时用几十次 |

**边界那句话比"我很能撤销"更可信**，因为它承认了 git 的存在，用户还能用手里的
`git status` 交叉验证我们：

> **我负责 git 覆盖不到的那部分 —— 未跟踪文件，以及 shell 的副作用。**
> **已跟踪文件请用 git，我不跟你抢。**

## 三、明确**不做**的清单（免得顺手抄了）

| 不做 | 原因 |
|---|---|
| **delta / 锚点链 / 更花哨的存储** | 第二节：优化的是我们已经解决的那一栏（存字节），而瓶颈在读目录 |
| **会话级 / 整树回滚** | 违反 `guard.ts:65-70` 自己写下的归属原则 |
| **硬啃 OS 沙箱** | 项目自己实测过：Windows 上免提权 AppContainer **确定性地无法执行打包的 node.exe**；限制型令牌要保留 logon SID + Everyone 否则子进程 `0xC0000022`。收益是"对抗性安全"，而本地编码助手面对的是**手滑不是对抗** |
| **代码库索引 / RAG / 内联补全** | 那是 Cursor 的战场，我们在这条线上没有优势；而我们的优势（可解释、可拒绝、可撤销，**连 shell 副作用一起**）恰恰是竞品文档里写着的洞 |
| **AES-GCM + 自管密钥** | 同机可读；要做走 **DPAPI**（Windows 平台能力，不是自研加密） |

## 五、我建议的第一件

**第 5 条（把 changeset 呈现成 diff）**，理由：

- 它是**最高频**的（每小时几十次，而不是一年几次）；
- 它**不新增任何机制、存储或概念** —— 数据全在，只差把路径带出来 + 画出来；
- 它**不动 `guard.ts` 一行边界语义** —— 不引入任何新的正确性风险；
- 它让第 2 条（撤销入口）有了自然的落点：**先能看见改了什么，再决定要不要撤**。
