# 破坏性与资源护栏

> 两类事故的共同点：**它们不产生任何"内容"** —— 没有密钥、没有可疑字符串。
> 所以输出审核对它们完全不适用，而审批卡只给用户一行他无法评估的命令。

## 1. 现状（代码里的事实）

| 环节 | 现状 | 出处 |
|---|---|---|
| 命令默认策略 | `workspace-write` 下 `commandDefault = 'ask'` | `policy/types.ts` |
| deny 表 | **只有七条**：`sudo`、`mkfs`、`diskutil eraseDisk`、`Format-Volume`、`shutdown`、`reboot`、`Set-ExecutionPolicy` | `policy/types.ts` |
| 超时 | `DEFAULT_TIMEOUT_MS = 30_000` | `tools/types.ts` |
| 进程树 | 超时后 `taskkill /T /F`（**事后反应**，无 Job Object） | `tools/kill-tree.ts` |
| 输出捕获 | 先写临时文件，**进程结束后 `readFile` 整个读进内存**，才截断到 60 000 字符 | `tools/command-tool.ts` |
| 快照范围 | 只走工作区；排除 `node_modules`/`dist`/`build`/`out`/`target`/`.next`/`.venv`/`coverage`/`.cache` 等；单文件上限 20 MiB | `recovery/types.ts` |
| 有后台作业时 | **完全不做事务**（归属无法确定） | `recovery/guard.ts` |

最后一行是最隐蔽的缺口：**只要模型起了一个 `npm run dev`，整段撤销能力就失效**。

## 2. 破坏性命令

### 2.1 过程

```
模型想清理 → run_command('rm -rf …') 或 ('del /s /q …')
 → 策略：命中不了七条 deny → ask
 → 审批卡：只显示命令原文（可以被 -EncodedCommand 或变量拼接写成读不懂的东西）
 → 用户点允许 → 以当前用户、Medium 完整性、无沙箱执行
 → 恢复层：begin 全树快照（工作区）→ 执行 → commit
 → 后果取决于打哪儿
```

### 2.2 能不能撤，取决于打哪儿

| 删除目标 | 能撤销吗 | 原因 |
|---|---|---|
| 工作区外 | **不能** | 快照只走工作区根 |
| 工作区内普通文件 ≤ 20 MiB | 能 | `removed` 有 blob |
| 工作区内 `.git` | 能（默认排除里没有 `.git`） | 快照包含它 |
| 工作区内 > 20 MiB | 不能 | 上限，只登记为"盲区" |
| 工作区内排除目录 | 不能 | 不扫 |
| **同时有后台作业在跑** | **完全不能** | 守卫跳过事务 |
| 任何目标，`rm`/`del` | **没有回收站** | 两者都是直接删 |

### 2.3 三层改动

**第一层：结构化清理工具（唯一合法入口）**

```
delete_paths({ paths: string[], why: string })
move_path({ from: string, to: string })
```

它拿到 `rm` 永远拿不到的三样：逐条路径围栏、卡上可显示的影响面（"将删除 3 个路径，共 1 247 个文件、86 MB"）、一次可撤销的事务。

配套两条硬要求：

1. **拒绝文案要教路**：`rm` 被 deny 时返回"要删文件请用 `delete_paths`，它可撤销"，否则模型会换着写法重试，白烧几轮
2. **系统提示写明 `run_command` 的职责边界**：跑构建、跑测试、跑工具 —— 不承担改文件系统

**第二层：扩大 deny 表**

```
rm -r / -f / -rf / --recursive / -fr …（各种拼法）
del /s、del /q、erase /s、rd /s、rmdir /s
Remove-Item -Recurse、ri -Recurse
git clean、git rm -r
robocopy /MIR、rsync --delete（源为空 = 清空目标）
find … -delete、truncate、fsutil file setzerodata
```

外加一条低成本规则：`-EncodedCommand` / `-enc` / `frombase64string` 一律 deny。理由不是"它会删东西"，而是**审批卡对用户没有意义** —— 人无法在点"允许"前读懂 base64 的 PowerShell。不能评估的东西不该让人签字。

**第三层：事后审计 + 自动还原（真正抬下限的那条）**

黑名单会漏，但**结果不会漏**：

```
run_command 结束
 → 事务 diff 里有 removed
 → 而这次工具不是 delete_paths
 → 从 blob 还原这些文件
 → 发一条可见事件：「这条命令删了 12 个文件，已自动还原。要删请用 delete_paths。」
```

它不依赖字符串：模型把删除藏在 `powershell -EncodedCommand`、`node -e "fs.rmSync(...)"`、`python -c "shutil.rmtree(...)"` 里，只要删的是**工作区内**的文件，diff 就会看见。

### 2.4 边界（拦不住的）

| 边界 | 说明 |
|---|---|
| 工作区外无验尸 | 快照只走工作区，外面的删除既不能预判也不能还原。只有 OS 沙箱能补 |
| `make clean` / `npm run clean` 内部的删除 | 我们只审模型**打出来的那行字**；构建脚本里的 `rm` 是用户自己的代码 |
| `-EncodedCommand` 之外的混淆 | `certutil -decode`、变量拼接、delayed expansion —— 字符串永远追不完；只有工作区内的能靠第三层捞回 |

## 3. 资源耗尽

### 3.1 现状的两个问题

**问题一：没有硬上限。** 进程数、内存、CPU 时间都没有约束，只有 30 秒墙钟超时 + `taskkill /T`。fork bomb 在 30 秒里能生出几千个进程；换过进程组的子进程会活下来成为孤儿。

**问题二：我们自己是放大器。**

```
子进程 stdio → 临时文件
子进程结束后 → readFile 整个文件进内存 → 才截断到 60 000 字符
```

`DEFAULT_MAX_OUTPUT_CHARS` 只限制"模型看到多少"，**不限制我们写多少、读多少**。一个 `yes` 跑 30 秒能写出 GB 级临时文件，然后被整个读进内存 → 守护进程 OOM，会话全丢。

### 3.2 Job Object：四个维度一个对象

| 上限 | 值（示例） | 挡住什么 |
|---|---|---|
| `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` | 64 | **fork bomb**：第 65 个进程创建不出来 |
| `JOB_OBJECT_LIMIT_PROCESS_MEMORY` | 2 GB | 单进程吃光内存 |
| `JOB_OBJECT_LIMIT_JOB_MEMORY` | 4 GB | 整棵树吃光内存 |
| `JOB_OBJECT_LIMIT_JOB_TIME`（CPU 时间） | 120 s | 死循环烧 CPU（比墙钟准，`sleep` 不算） |
| `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` | 开 | **daemon 崩了整棵树跟着死** —— 孤儿归零 |

关键差别：现在是**超时后反应**（30 秒里已经生了几千个进程），Job Object 是**事前上限**（第 65 个根本创建不出来）。

**退路（暂时不引 FFI）**：每 200 ms 数一次子孙进程数与总 RSS，超阈值就 `killTree`。比 Job Object 慢半拍，但把"30 秒无人管"变成"0.2 秒内掐断"，且零依赖。

### 3.3 写崩磁盘

按"跟踪它写的那些文件的大小"做不干净：归属算不准（别的进程也在写）、有竞态（看到 1.2 GB 时已经写完）、范围覆盖不了（能写任何地方）、**0 字节与稀疏文件完全看不见**。

干净的度量是**进程树一共写了多少字节** —— Job Object 自带：

```
QueryInformationJobObject(JobObjectBasicAndIoAccountingInformation)
  → WriteTransferCount   （整棵树累计写入字节，含所有子孙）
```

每 250 ms 查一次，超过预算（默认 1 GB）就杀树，并报"在 4 秒里写了 1.2 GB，已中止"。

三层一起：

```
事前    剩余空间 < 2 GB → 拒绝（fs.statfs）
过程    每 250 ms：写字节 > 预算 / 新增文件数 > 预算 / 剩余跌破底线 → 杀树
事后    事务 diff 精确报「新增 N 个 / 修改 M 个 / 共 X MB」，一步 delete_paths 清理
```

**新增文件数**是另一条独立预算（0 字节文件与目录洪水按字节测不到，占的是 MFT）：

- 结构化工具：每次调用 +1，精确
- `run_command`：每 100–250 ms 数一次工作区 entry 数

**归因要诚实**：

```
磁盘少了 1.2 GB（本次命令写入 40 MB）→ 大概率不是它
磁盘少了 1.2 GB（本次命令写入 1.1 GB）→ 就是它
磁盘少了 1.2 GB（无法归因）           → 如实说无法归因
```

唯独**我们自己起的后台作业**要算我们的账（`npm run dev` 挂一天是典型的"慢慢写满盘"）。

### 3.4 0 字节文件：禁"空"禁不到点上

空文件有合法用途：`__init__.py`（Python 包标记，必须空）、`.gitkeep`、`.nojekyll`、占位文件、测试夹具的空输入。一条"禁止创建 0 字节文件"会把它们全拦掉。

而洪水的真正形态不是 0 字节：`for /l %i in (1,1,1000000) do echo x> f%i` 每个文件 2 字节，按"内容为空"一个都看不见，照样写死盘（占 MFT 与目录项）。

所以：

- **不禁**创建空文件
- **禁**把已有文件截断为空（`write_file({ content: '' })` 打在已存在的文件上 = 静默数据销毁）；要清空请用 `delete_paths` 或在 `edit` 里删到空
- 真正管的是**文件数预算**

### 3.5 无限循环：静态检测只能当提示

能查到的（模板化）：`while (true)`、`while(1)`、`for(;;)`、`loop {}`、`while True:`、`for (i <= 1e8)`、`setInterval(…, 0)`、无终止条件的递归。

查不到的：条件恒真但推导出来的、事件循环不退出（`server.listen()`）、逻辑死循环、`eval(base64)`。

误报成本很高：`npm run dev`、`vite --watch`、`jest --watch`、`python -m http.server` 全是"看起来死循环"的合法命令。

所以定位是**提示**：

- 范围只限**本次会话新建的文件**与**内联脚本**（`node -e`、heredoc）
- 只在"无 `await` / 无 sleep / 无 I/O"的紧循环上出提示
- 不阻断，卡片上多一行"这个脚本看起来是紧循环，可能一直不退出"

「先试跑一次再真跑」不成立：试跑有副作用（会写文件、会 spawn）、预测不了（停机问题）、上限选错轴（fork bomb 的伤害是进程数，128 MB 挡不住 3000 个 128 MB 进程）。**不要预测，直接约束。**

## 4. 日志增长

### 4.1 现状（比想象的小）

```
事件日志：1 840 个会话，共 3.4 MB，最大一个 760 KB
恢复层 blob：已有 prune —— 只保留被最近 100 个事务引用的快照与 blob
```

真正会长的是两处：`tool_settled` 里存**完整 content**（一次 `grep -r` 60 KB）；`jobs/<id>/stdout.log` 无上限。

### 4.2 精简要撞一条不变量

事件日志是**唯一事实来源**，删内容 = 让"重放必须逐字一致"作废。所以清理必须是：

1. 只删 tool 输出的**正文**，保留摘要与计数（重放后显示「输出已清理（原 58 KB）」）
2. 记一条 `log_trimmed` 事件：范围、删了多少字节、哪个会话 —— 清理本身可审计
3. 上限驱动：每会话 200 MB 触发；保留最近 7 天；先算收益再动手
4. 永久删要用户按一次；自动清理只删正文

这样一致性从"逐字"降级为"结构一致 + 明确标注"，降级是**可见的**而不是静默的。

顺带补：命令捕获的临时文件在 `finally` 删；daemon 崩了会留，补**启动清理**（`mvs-*` 前缀、超过 24 小时的目录）。

## 5. 验收标准

一条能说明这套东西管不管用：

> `%0|%0` 的批处理从启动到被掐断 ≤ 1 秒，报告写明"因进程数超过 64 而中止"，磁盘剩余空间没跌破底线。

现在的行为：30 秒后才动手，临时文件几 GB，撤销能力同时失效。

## 6. 落地顺序（每条都能单独回退）

1. **修输出捕获**（流式 + 硬封顶 8 MB + `statfs` 哨兵）—— 纯 Node，无依赖，收益最大
2. **结构化清理工具**（`delete_paths` / `move_path`）+ 系统提示改边界
3. **deny 表扩展** + 拒绝文案教路
4. **事后审计 + 自动还原**（工作区内删掉的自动捞回）
5. **Job Object**（进程数/内存/CPU/写字节）+ 250 ms 轮询；无 FFI 时先用 watchdog
6. **文件数预算**（结构化工具精确计数 + shell 轮询）
7. **日志 trim + 启动清理**
8. **死循环提示**（只提示不拦）

前四条不需要任何原生调用，能立刻做完；第 5、6 条与沙箱的 `sandbox-worker` 共用同一条原生通道。
