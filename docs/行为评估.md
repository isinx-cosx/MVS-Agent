# 行为评估

> 单元测试守的是**代码正确性**：给定输入，函数返回什么。
> 这份东西守的是**行为**：给一个真实任务，它有没有按能接受的方式做完。

## 1. 为什么需要它

改一句系统提示、换一档压缩比例、装一个技能、接一个新模型 —— 这些都**不改变任何单元测试的结果**，但会改变 agent 的表现。没有这个东西，就只能靠"感觉好像变好了"。

它也不是"跑分"。它回答三个具体问题：

1. 这一轮**跑完了吗**（没跑完的结论不能说通过，也不能说模型不行）
2. 它**做对任务**了吗（文件内容对不对、有没有碰不该碰的、该不该问人）
3. 有**产品层面**的问题吗（挂着的工具调用、悬空的审批、坏日志、超时）

第 3 类与模型无关，任何模型跑都不该出现；第 2 类才是模型的锅。报告里分开列，因为混在一起会得到"失败 7 个"这种没法行动的数字。

## 2. 一次运行长什么样

```
npm run eval                          # eval/scenarios 下全部
npm run eval -- --only write-file     # 只跑一个
npm run eval -- --profile ollama      # 指定模型档案
npm run eval -- --scripted --scenarios eval/scenarios-scripted   # 自检，不涉及模型
npm run eval -- --out report.json     # 另存 JSON 报告
```

每个场景：

```
临时家目录 ─┐
临时工作区 ─┴→ 写夹具文件 → 起 Runtime → 开会话 → 设模式
             → 发 prompt（等它跑完，带超时）
             → 读投影 / 事件 / 事务 → 断言 → 一份结果
```

**每个场景一个临时 home**：上一条留下的 `state.json`、恢复层事务、会话日志都会污染下一条的观察（尤其是"可撤销事务数"）。

## 3. 场景文件

`eval/scenarios/*.json`：

```json
{
  "id": "edit-existing",
  "description": "改一个已存在的文件：内容要落盘，而且不该顺手动别的文件",
  "prompt": "把 greet.js 里的 Hello 改成 Hi，只改这一处。",
  "files": { "greet.js": "console.log('Hello')\n", "keep.js": "console.log('keep')\n" },
  "expect": {
    "finalText": "/Hi|greet/",
    "fileContains": { "greet.js": "Hi" },
    "maxSteps": 5
  }
}
```

可用的期望：

| 字段 | 含义 |
|---|---|
| `finalText` | 最终正文匹配（子串，或 `/正则/`） |
| `toolCalled` | 至少调用过其中之一 |
| `toolAllCalled` | 必须全部调用过 |
| `toolNotCalled` | 一个都不许调用 |
| `fileContains` | 工作区文件必须包含这些内容 |
| `fileMissing` | 这些文件必须不存在 |
| `maxSteps` | 最多几步（一次用户消息可能触发多轮工具） |
| `approvalAsked` / `noApproval` | 该不该问人 |

其它字段：`files`（初始夹具）、`mode`（默认 `workspace-write`）、`timeoutMs`（默认 120 秒）、`autoApprove`（默认 true —— 让场景能跑完，该不该问用上面的断言验）。

## 4. 不变量（每个场景都查）

| 不变量 | 违反的后果 |
|---|---|
| 这一轮结束了（`status !== running`） | 界面永远显示"运行中" |
| 没有未结算的工具调用 | 会话卡在 `interrupted`，用户只能重启 |
| 没有悬空的审批 | 同上 |
| 日志能解析（`malformed === 0`） | 重放时会丢步骤 |
| 没有超时 | 结论既不能说通过，也不能说模型不行 |

## 5. 自检（`--scripted`）

没有可用模型时（本机没起 Ollama），这个工具仍然要能证明**自己是活的**：脚本化模型按固定脚本先调一次 `read_file`、再给一句收尾。

`eval/scenarios-scripted/` 就是给这条路径用的两个场景。它们验的是**工具链**：能不能建工作区、能不能跑完一轮、投影与事务读得对不对、报告与退出码对不对。

报告里 `meta.scripted = true`，汇总行也会明说一句：

> ⚠ 自检报告：只证明这套工具是活的，不构成对模型行为的任何结论。

**这一句不能省。** 一份被误读的评估报告比没有更糟 —— 它会让人以为"模型通过评估了"，而实际上评估根本没跑模型。

## 6. 退出码与报告

```
有失败 → 1（否则没人会去看）
全部通过 → 0
场景目录有问题（坏 JSON、缺 id/prompt）→ 2
```

`--out report.json` 存完整报告：`meta`（时间、模型、是否自检）+ 每个场景的 `observations`（正文、工具、步数、审批数、事务数、耗时）+ 分好类的 `failures` + `summary`。

## 7. 它不做什么（写清楚免得被当成万能）

- **不做统计显著性**：一个场景跑一次。要比较两个模型得自己重复跑、自己看方差。
- **不替代人工看**：断言只覆盖"能不能接受"，覆盖不了"回答得好不好"。
- **不测成本**：用量与成本在投影里（`totalUsage` / `cost`），但评估判定不看它 —— 便宜不是正确。
- **不跑在 HTTP 上**：直接构造 Runtime + Session，比走服务端少一层失败来源；代价是没覆盖传输层（那由 `test/server.test.ts` 覆盖）。
