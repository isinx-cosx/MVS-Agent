# 安全边界：现在保证什么、保证不了什么

> 这份文档说的是**当前实现**的边界，不是"沙箱技术能做到什么"。
> 后者已经在另外三份研究里写透了，这里**不重复**，只回答一个问题：
> **今天这套东西，哪些是真的强制的，哪些只是靠人看着。**
>
>   研究部分：`design-notes-sandbox-permissions-reversibility.md`（设计取舍）、
>   `os-sandbox-findings.md`（Windows 实测）、`sandbox-platform-matrix.md`（同类产品怎么做）
>
> ⚠️ **每条断言都带 `文件:行`。** "我们有沙箱"这句话最容易变成能力宣传，
> 而能指到代码的断言才可反驳。**改了对应代码就要改这里** ——
> 一份和实现不一致的安全文档，比没有文档更糟。

---

## 零、一句话结论

**文件操作有强制边界；命令与网络没有。**

- 对**文件工具**：越出工作区的路径会被拒绝，而且是按 `realpath` 判的，符号链接绕不过去。
- 对**命令**：给的是一个 shell，能做你这个用户能做的任何事。策略拦得住典型形态，拦不住语义。
- 对**网络**：完全敞开，没有任何 host 策略。

所以准确说法是：**有策略强制，没有隔离。** 有人盯着的时候两者效果接近；
在自动放行 / `full-access` 下，差别就是全部。

---

## 一、真正强制的（进程内，不依赖人）

| 保证 | 机制 | 证据 |
|---|---|---|
| 文件工具不能读写工作区之外 | 所有文件类工具走同一个入口，`realpath` 解析后判是否在根内 | `src/tools/paths.ts:20`（`resolveInsideRoot`）、`:28`（`safeRealpath`）；调用点 `src/tools/file-tools.ts:45,112,159,212`、`src/tools/edit-tool.ts:72` |
| 越界时**明确拒绝**，不是静默失败 | 策略层第二次判断，带人话说明 | `src/policy/policy.ts:251`（`isInside`）、`:397-403`（`路径越出工作区，当前模式不允许：…`） |
| 命令的工作目录被限制在工作区内 | 参数 `cwd` 走同一个 `resolveInsideRoot` | `src/tools/command-tool.ts:92-95` |
| 每个工具声明自己的破坏性 | `fileWrite: 'none' \| 'workspace' \| '任意'`，模式与它共同决定放行 | `src/policy/index.ts:54` |
| 命令不是靠字符串前缀判定 | 内容检查（注释里点名"前缀匹配抓不住管道"） | `src/policy/policy.ts:122` |
| 只读命令可以被**证明**，而不是被"允许" | 三条硬规矩：出现任何 shell 元字符一律不认；不做前缀匹配而做"程序+子命令+参数形状"匹配 | `src/policy/read-only.ts` |
| 出厂允许列表**是空的** | 这是刻意的：宽列表会覆盖 `npm publish` 和所有 postinstall | `src/policy/read-only.ts` 开头 |
| 动作前后整树快照（可逆性） | 唯一跨平台成立的承诺 | `src/recovery/guard.ts:6,11` |

## 二、只是审批的（人看着才成立）

- **`run_command` 的执行**：给的是 shell。上面那条"工作目录受限"限制的是 `cwd`，
  **不是命令能碰什么** —— `run_command("echo x > ../外面/y")` 不受路径检查约束。
- **审批本身**：`allow → ask → deny` 的降级链（`src/policy/policy.ts:10`）意味着
  "没人应答时会被拒绝"，这是对的；但它同时意味着**审批不是隔离**。
- **抗疲劳熔断**：连续 3 次 / 累计 20 次打回后，剥夺 `allow` 规则的批准权
  （`src/policy/policy.ts:7,289-302`）。它防的是"用户开始闭眼点允许"，
  不防"模型想做坏事"。

---

## 三、保证不了的（诚实清单）

1. **没有操作系统级隔离。** 搜过作业对象、受限令牌、AppContainer、`sandbox-exec`、
   `bubblewrap`、`seccomp` —— `src/` 里**一处都没有**。判断全在进程内，
   而工具进程跑在**当前用户的完整权限**下。研究与实验代码留在 `tools/find-token.mjs`
   与那三份文档里，**没有接进产品路径**。

2. **`run_command` 的语义拦不住。** 路径级 confinement 对"一条命令"没有意义。
   典型形态（管道、重定向、`curl | sh`）有内容检查挡着，变形挡不住。

3. **网络敞开。** `src/tools/web-tools.ts:225,467` 直接 `fetch`，没有 host 白/黑名单。
   配合第 2 条，这是一条完整的**数据外送通道**：读工作区文件 → 发出去。

4. **`full-access` 等于交钥匙。** 它是模式之一（`src/policy/types.ts`），
   不是"更快的工作区可写"。

5. **命名有个坑**：错误类型里有个 `'sandbox'`（`src/tools/command-tool.ts:324`、
   `src/tools/types.ts:162`），它指的是"命令**执行被挡**"，**不是**操作系统沙箱。
   读代码的人会误解，写文档的人更容易误解 —— 改名前先在文档里说明。

## 四、出厂默认姿态

```
权限模式      workspace-write（`/state` 的 config.permissions.defaultMode）
允许列表      空
只读判定      能证明才自动放行；证明不了照常问
熔断          连续 3 次 / 累计 20 次打回 → 剥夺 allow 的批准权（不强制拒绝）
降级          allow → ask；无人可应答时 ask → deny
恢复          写类工具动作前后整树快照
```

## 五、威胁模型：防谁

**防的是"模型判断失误 + 提示词注入"，不是"有人主动攻击这台机器"。**

这个区分决定了上面那张表的含义：模型读到工作区里一个被精心构造的文件时，
它可能被诱导执行任意命令 —— 而第 2、3 条意味着**那时没有第二道墙**。
文件工具的边界在这种情况下仍然是有效的（它拦的是路径，不是意图）。

---

## 六、后续顺序（先功能后安全，已定）

1. `run_command` 的边界：工作区外的写入至少要拦，或者把"任意命令"明确标成
   "等于把这台机器的权限交出去"（现在的措辞没到这一步）。
2. 网络显式开关：能不能对外发请求，应该是显式的、默认关闭的。
3. 真隔离要上操作系统能力（作业对象 / 受限令牌 / AppContainer / 容器），
   但那有已知代价 —— 见 `os-sandbox-findings.md`（AppContainer 跑不了工具链）。

---

## 七、维护约定

- 每条断言都指 `文件:行`；**代码改了这里必须跟着改**。
- 新增任何"强制"类保证时，先问一句：**它在没人应答、且模型主动想绕的情况下还成立吗？**
  只有成立才写进第一节，否则写进第二节或第三节。
