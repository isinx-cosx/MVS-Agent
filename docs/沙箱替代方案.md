# 沙箱替代方案

> 本文推翻 `os-sandbox-findings.md` 里「免提权没有可行解」的结论。
> 结论变了，原因是**新的实测数据**，不是想法变了。

## 1. 先更正旧结论

旧文档写的是：

> 免提权的跑不了工具链；能跑工具链的全都要提权或重启。

其中「低完整性（Low IL）」那一行标的是「半（只挡写）/ 需 native / 挡不住读」，**没有实测**。

实测（本机一个正在运行的进程，不是构造出来的环境）：

| 检查 | 结果 |
|---|---|
| 令牌完整性级别 | **Low Mandatory Level**（`S-1-16-4096`） |
| Administrators 组 | **仅用于拒绝**（deny-only） |
| 跑 node | 成功（v26.3.1） |
| 跑 PowerShell | 成功（脚本本身） |
| 读用户目录 | **允许**（列出 107 项） |
| 写 `%TEMP%` | **拒绝** `Access to the path … is denied` |
| 写工作区 | **拒绝** 同上 |
| 回环 HTTP | **通**（拿到 403，说明连接建立成功） |

**受限令牌 + 低完整性，免提权，能跑真实工具链，写不出去，读照旧，网照旧。**

旧的「受限令牌实测失败（`0xC0000022`）」与这条不矛盾：那次把限制集设成 `BUILTIN\Users`，**把自己的用户 SID 也限制掉了**，连自己的 profile 都进不去。而实测观察到的形状是：

```
用户 SID          保持原样
Administrators    deny-only（保留 SID，只为"拒绝"生效）
完整性级别         Low
```

差别在「限制什么」：用 `WRITE_RESTRICTED` 只限制**写**，再加上降完整性级别 —— 工具链照常，写被挡住。

## 2. 为什么优先做工具层而不是沙箱

| | 沙箱 | 工具层 |
|---|---|---|
| 决定依据 | 按**进程** | 按**内容/路径** |
| 能解释吗 | 不能，只能一刀切 | 能（"这一步要删 40 个文件，理由是…"） |
| 能撤销吗 | 不能，只防不治 | 能（已有整树快照 + 事务） |
| 跨平台 | Windows/macOS/Linux 三套 | 一套 |
| 需要权限 | 低完整性免权限；换用户要管理员 | 免权限 |

威胁模型是**手滑，不是对抗**（旧文档第 2 条结论仍然成立）。在这个模型下，工具层能覆盖八成，而沙箱补的是"硬写入边界"。

所以定位写成一句话：

> **工具层是主线，低完整性是加固，WSL/Windows Sandbox 是高级选项。**
> 三者不是替代关系，是纵深。

## 3. 分层

### 第 0 层：已有（今天就有）

路径围栏（`resolveInsideRoot`）+ 策略模式 + 恢复层快照 + 审批。它防不住 `run_command` 的副作用，作用是"平时不出事"。

### 第 1 层：工具层护栏（主线，见另两份文档）

- `docs/输出审核.md` —— 模型能看到什么（读的问题）
- `docs/破坏性与资源护栏.md` —— 模型能做什么（写、删、资源的问题）

### 第 2 层：低完整性 + 受限令牌（加固，免提权）

**机制**（全部是公开 Win32 API，按 MSDN 写）：

```
OpenProcessToken(GetCurrentProcess(), TOKEN_DUPLICATE | TOKEN_QUERY)
CreateRestrictedToken(token, WRITE_RESTRICTED, 0, NULL, 0, NULL, 0, NULL)
DuplicateTokenEx(...)                     → 主令牌
SetTokenInformation(TokenIntegrityLevel, { TokenIntegrityLevel, Low })
CreateProcessAsUser(..., CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT)
AssignProcessToJobObject(job, process)    → 资源上限 + 随 daemon 退出一起收
ResumeThread
```

`CreateRestrictedToken` 用 `WRITE_RESTRICTED`，让限制只作用于**写**。令牌是**自己主令牌的受限版**，所以 `CreateProcessAsUser` 不需要 `SeAssignPrimaryTokenPrivilege`（MSDN 明说，也正是实测到的事实）。

**唯一没闭合的一环：工作区要能写。**

Low 进程只能写标了 Low 的对象，所以要给工作区打标签：

```
icacls <工作区> /setintegritylevel (OI)(CI)Low
```

理论上不需要管理员（完整性标签走 `LABEL_SECURITY_INFORMATION`，要求对对象的 `WRITE_OWNER`，用户对自己建的目录本来就有）。**但这是关键假设，本机尚未实测。**

### 第 3 层：独立用户 + 按用户防火墙（严格模式）

第 2 层挡不住**读**和**联网**（同一个身份）。要挡这两样只有换身份：

1. 安装器一次性提权：建 `MVS-Sandbox` 用户（随机密码，DPAPI 加密）、工作区只给它 `Modify`、`New-NetFirewallRule -LocalUser` 按用户断网
2. 运行时（不提权）：`CreateProcessWithLogonW(..., LOGON_WITH_PROFILE)`

代价：首次登录建 profile 慢、拿不到用户级配置（`.npmrc`、`git config`），而后者正是"换用户跑"那条路最容易踩的坑。

### 第 4 层：WSL2 / Windows Sandbox

真边界，但要开功能、重启、占资源。本机 `wsl --status` 明确回「未安装适用于 Linux 的 Windows 子系统」。只对愿意付代价的用户开放，文档里如实标注前提。

## 4. 挡什么、不挡什么（不能含糊）

| 手滑形态 | Low IL | 工具层 |
|---|---|---|
| 文件写到工作区外 | 挡 | 挡（结构化工具）/ 部分（shell） |
| 删工作区外的文件 | 挡 | 部分 |
| 改注册表 `HKLM`/`HKCU` | 挡 | 部分 |
| 把 `%TEMP%` 塞满 | 挡 | 挡（环境重定向） |
| 覆盖工作区内的文件 | 放行（有恢复层） | 放行（有恢复层） |
| **读出密钥并发到网上** | **不挡** | 挡"模型知道"，挡不住"进程外发" |
| **无限循环 / 资源耗尽** | 不挡（只限内存/进程数，见资源护栏） | 靠 Job Object，不靠 Low IL |

界面和文档里**不许**把它叫"安全模式"。它能保证"没搞坏你的机器"，不能保证"没偷看你的文件"。

## 5. 待实测清单

| # | 假设 | 怎么测 | 失败时怎么办 |
|---|---|---|---|
| E1 | 非管理员能给自己的目录设 Low 标签 | **已实测通过**（非管理员账户）：`icacls <目录> /setintegritylevel (OI)(CI)Low` 返回 0，输出 `Successfully processed 1 files` | 回退：安装时提权设一次，或用沙箱子目录 |
| E2 | 受限令牌 + Low 能跑 node/npm/git | **令牌管线已实测通过**（`tools/sandbox-probe.mjs`）：`OpenProcessToken` → `CreateRestrictedToken(WRITE_RESTRICTED)` → `ConvertStringSidToSid(Low)` → `SetTokenInformation(TokenIntegrityLevel)` → `DuplicateTokenEx(primary)` 五步全 ok | 剩下的是 `CreateProcessAsUser` + Job Object（见 E5） |
| E3 | 工作区内写成功、区外失败 | 两边各写一个文件，看错误码 | 收窄/放宽标签范围 |
| E4 | 子进程继承（`npm` 会再 spawn `node`） | `npm run build` 之类多级派生 | 继承丢失则给每个进程显式建令牌 |
| E5 | Job Object 能收掉整棵树 | 起 fork bomb 再杀 daemon | 见资源护栏的 watchdog 退路 |
| E6 | 标签能恢复、崩了能修 | 手动杀 daemon 后检查标签 | 提供 `mvs sandbox repair` |

E1 成立与否决定第 2 层能不能做；不成立就退到"沙箱子目录 + 审批式回写"。

## 6. 实现形状

沿用 `tools/dialog-worker.mjs` 的模式：**独立的 Node 子进程负责原生调用**。

```
src/sandbox/spawn.ts       找 koffi；找不到就如实报"这台机器用不了第 2 层"
tools/sandbox-worker.mjs   koffi → 受限令牌 + Low + Job Object + CreateProcessAsUser
```

不放在 daemon 里：原生调用崩了不该带走守护进程；令牌与 Job 句柄本来就是进程级资源。

**失败必须可见**：拿不到令牌/DLL 时，命令不静默降级到无沙箱执行，而是回一条 `sandbox_unavailable`，由用户决定"这一次以无沙箱方式运行"。

## 6.1 实测进展：令牌管线已通

`tools/sandbox-probe.mjs` 用 koffi 直接走完五步，全部成功（非管理员账户）：

```
OpenProcessToken(TOKEN_ALL_ACCESS)                → ok
CreateRestrictedToken(WRITE_RESTRICTED)           → ok    只限制写，用户 SID 保留
ConvertStringSidToSid("S-1-16-4096")              → ok    Low 的 SID
SetTokenInformation(TokenIntegrityLevel, label)   → ok    降完整性级别
DuplicateTokenEx(..., TokenPrimary)               → ok    拿到主令牌
```

输出：`{"ok":true,"steps":{"open":"ok","restrict":"ok","sid":"ok","integrity":"ok","primary":"ok"}}`

**还没接的**：`CreateProcessAsUser`（用这个主令牌起进程）与
`SetInformationJobObject`（进程数/内存/CPU/写字节四个上限）。
这两步放在同一个 worker 里做 —— 它们共用同一个令牌与句柄生命周期。

踩到的两个 koffi 细节（写进这里的理由：下次不用再摸）：

1. `koffi.struct(...)` 必须在**任何引用它的 `func()` 之前**注册，否则报
   `Unknown or invalid type name`（把结构定义挪到 `koffi.load` 之后即可）
2. 传结构给 `SetTokenInformation` 时，参数类型要写 `TOKEN_MANDATORY_LABEL *`，
   写 `void *` 会得到 `Unexpected Object value, expected void *`
## 6.2 实测进展：进程起得来，Job 还挂不上

`tools/sandbox-worker.mjs` 已能把**受限 + 低完整性**令牌用到 `CreateProcessAsUser`：

```
steps: { token: "ok", job: "ok", spawn: "ok" }   ← 进程真的起来了
然后 AssignProcessToJobObject 失败（ERROR_ACCESS_DENIED）
```

原因不是代码写错，而是**本进程自己已经在一个 Job 里**（受限环境给每个命令套了一层）。
Windows 8+ 支持嵌套 Job，但把子进程塞进新 Job 要求它不是"父 Job 的成员"。

正确做法：**让子进程一出生就在 Job 里** —— `STARTUPINFOEXW` +
`InitializeProcThreadAttributeList` + `UpdateProcThreadAttribute(ProcThreadAttributeJobList)`。
这需要另一组结构体，是下一步。

所以在接上之前，worker 的能力边界是：**令牌可用、进程可起、Job 上限配得出但管不住**。
不要把它当成"已经有资源上限"。

## 6.3 探针：属性列表第一步通了，第二步还没通

`tools/joblist-probe.mjs`（只做属性列表，不接进程）：

```
第一次 InitializeProcThreadAttributeList(NULL, 1, 0, &size) → false, size = 48   ✓ 符合预期
第二次 InitializeProcThreadAttributeList(buf, 1, 0, &size)  → false, errno = 0   ✗
```

第一次拿到 48 字节（Windows 的实现相关大小，正常）；第二次失败且 `GetLastError` 为 0，
说明**不是系统拒绝，而是我们的参数传递不对**（大概率 `BOOL` 用 1 字节的 `bool`
去映射 4 字节的 `BOOL`，或者 `_Inout_ uintptr *` 在第二次调用里的语义没对上）。

下一步应该用 `int32` 代替 `bool` 做 BOOL 参数类型，并把 `lpSize` 的第二次调用改成
传缓冲区的**实际大小**（48，而不是 48+64）。这是下一轮的第一件事。

在那之前，**不要**把这个属性列表接进 `CreateProcessAsUser`：上一版直接接的结果是
`0xC0000005`（访问违例）。探针跑通再接，是这个文件存在的原因。

## 6.4 接上了：进程一出生就在 job 里

`ProcThreadAttributeJobList` 打通（探针先绿，再接线）：

```
{"ok":true,"steps":{"token":"ok","job":"ok","spawn":"ok","jobAttached":"ok"},
 "exitCode":0,"timedOut":false,"writeBytes":0}
```

这意味着四件事同时成立：受限令牌（只限写）、低完整性、Job 上限生效、整棵树可被
`KILL_ON_JOB_CLOSE` 带走。**护栏第 5 步从这里开始有硬上限。**

关键细节（都是踩出来的）：

1. `BOOL` 用 **`int32`**，不要用 `bool`（Win32 BOOL 是 4 字节）
2. `InitializeProcThreadAttributeList` 两次调用：第一次 `NULL` 只为拿 size（实测 48），
   第二次 `lpSize` 必须**等于缓冲区大小**
3. `UpdateProcThreadAttribute` 的 `lpValue` 是**指向句柄的指针**（写进 `Buffer` 再传）
4. `CreateProcessAsUserW` 的 startup 参数要声明成 `STARTUPINFOEXW *`（写 `void *` 会报类型错）
5. 用了 JobList 之后**不要再调** `AssignProcessToJobObject` —— 进程已经在 job 里，
   再挂一次会被拒绝（这正是上一版失败的原因）

**还剩一个缺口**：stdout/stderr 通过继承句柄没接上（子进程读到空）。当前只能在
命令行里自己重定向（`cmd /c "... > out.txt"`），或者后续换成显式 `CreateFileW` 的句柄。

## 6.5 成了：E2 / E3 / 进程数上限全部实测通过

`tools/sandbox-run.mjs`（从矩阵里已跑通的那一档抽出来的）现在能真正执行命令：

```
{"ok":true,"steps":{"token":"restricted-low","job":"ok"},"pid":7580,
 "exitCode":0,"timedOut":false,"stdout":"v26.3.1\r\n","stderr":""}
```

**E3（写隔离）实测**：

```
区内写（目录打 Low 标签）:  exitCode 0   inside.txt 存在
区外写（普通目录）:         exitCode 1   stderr="Access is denied."   outside.txt 不存在
```

**进程数上限实测**（`--max-processes 8`，命令试图起 80 个子进程）：

```
exitCode 1，stderr 里 80 行 "Not enough quota is available to process this command."
```

上限是真生效的 —— 这就是 fork bomb 被挡住的样子。

### 之前一直失败的两个真原因（都是工具用法，不是 Windows 语义）

1. **`PROCESS_INFORMATION` 必须用 Buffer 承接。**
   传 JS 对象时 koffi **不回写**：`CreateProcess*` 返回 1、`GetLastError` 是 0，
   而 `pid` 永远是 0、`hProcess` 是 NULL。我前几轮就靠那个返回值判断"起来了"，
   于是得出一串错误结论（"令牌有限制""命令不执行"）。改成 `Buffer.alloc(sizeof)` 之后
   三个对照档**立刻**都拿到真 pid。
2. **命令行不能把每个 token 都加引号。**
   `"cmd.exe" "/c" "echo x > y"` 会让 cmd 报错（stdout 68 字节、exitCode 1）。
   正确形态是 `"<exe>" /c "<整条命令>"`。

第 1 条是本轮最贵的一课：**一个检查通过了，不代表它检查的是你以为的东西**
（AGENT.md §七.2 原话）。`raw=1` 被我当成了"进程起来了"，而它只是"函数返回了真值"。

### 还没通的

- **写字节计数**：`QueryInformationJobObject` 没把 `WriteTransferCount` 取回来
  （`fsutil` 写了 1 MB，结果里没有 `writeBytes` 字段）。结构体布局还要对一遍。
- **接进 `run_command`**：`tools/sandbox-run.mjs` 现在是一个独立 CLI，
  还没被 `src/tools/command-tool.ts` 调用（计划用 `MVS_SANDBOX=low-il` 开关）。

## 6.6 Low 标签：沙箱能写工作区的前提（已做）

打开沙箱后，Low 进程**只能写打了 Low 标签的目录**。所以这一步不是可选优化，
而是"沙箱能不能用"的前提。

`src/sandbox/label.ts` + `npm run sandbox:label`：

```
npm run sandbox:label -- <目录>…          # 打 Low（含子项，(OI)(CI)）
npm run sandbox:label -- --check <目录>…  # 读当前标签
npm run sandbox:label -- --remove <目录>… # 恢复 Medium
```

- 用 `icacls /setintegritylevel`，**只加完整性标签、不动 DACL**（有测试钉住：
  打标签之后当前进程照常读写）
- `MVS_SANDBOX=low-il` 时守护进程在挂载工作区那一步自动打标签；失败会写 stderr
  说明原因（用户可能没权限改那个目录），不静默跳过
- 路径不存在时 `icacls` 也可能返回 0，所以测试用"沙箱真的写一次"来验证，而不是看返回码

实测（`test/sandbox-label.test.ts`，4 条）：

```
打上 Low → integrityOf = Low → 撤销 → Medium
路径不存在 → ok: false（不假装成功）
打了 Low 的目录里用沙箱写 → 成功；写区外 → 文件根本不存在
打标签后当前进程照常读写 → 说明没动 DACL
```

## 6.7 联网收口：命令不许上网，联网只走 `web_fetch` / `web_search`

沙箱只限制**写**，不限制网络。所以"读到密钥然后 `curl` 发出去"这条路是通的，
而且它的 stdout 只有 `OK` —— 审核连看都看不到。

挡在**发起连接**这一步，而不是看输出那一步：20 条规则（`curl` / `wget` /
`Invoke-WebRequest` / `Invoke-RestMethod` / `Start-BitsTransfer` / `nc` / `ssh` /
`scp` / `ftp` / `tftp` / `nslookup` / `Test-NetConnection` / `git push` / `npm publish` …），
文案指向 `web_fetch` / `web_search`。

**出口是必须的**：`npm install` 就是联网的。`MVS_ALLOW_NET=1` 会跳过所有
`tag: 'network'` 的规则 —— 否则用户只有"改源码"和"关掉策略层"两条路。

**这一层挡不住的**：解释器。`node -e`、`python -c`、PowerShell 一行都能开 socket。
那需要网络命名空间或过滤驱动，不是这一层能做的。写在这里，是因为下一个人一定会问。

## 7. 明确不做

| 不做 | 原因 |
|---|---|
| 自研 OS 级沙箱 | 两条免提权路线已实测否定，第三条要安装期提权 |
| AppContainer 硬啃 | 实测中目录枚举与映像加载确定性失败，根因未查明；不如走低完整性 |
| 把"防对抗"写进产品承诺 | 工具层 + 低完整性都挡不住蓄意外发 |
