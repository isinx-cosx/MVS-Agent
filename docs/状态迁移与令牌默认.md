# 状态迁移与令牌默认

> 两件 P0：「数据能不能安全换代」与「同机其他程序能不能随便驱动这个 agent」。
> 两件互不依赖，可以分开做、分开回滚。

---

# 一、状态迁移

## 1. 现状：三个文件都有版本号，但三种用法，全都不对

| 文件 | 版本字段 | 现在怎么用的 | 问题 |
|---|---|---|---|
| `state.json` | `version: 1`（`STATE_VERSION`） | **写了，从没读过** | 版本形同虚设 |
| `config.json` | `version: 1`（`CONFIG_VERSION`） | 不等于当前就**记一条 warning，然后照常解析** | 旧程序读新配置：字段静默丢掉，写回一次就永久没了 |
| `checkpoint.json` | `version`（`CHECKPOINT_VERSION`） | 不等于就**返回 null** | 完全静默：会话的 turn/step/status 归零，用户不知道原因 |
| `events.jsonl` | 无 | 靠 `rebuildMessages` 的宽容解析 | 只能"读得懂"，不能"升版本" |
| `.mvs/skills.json`、`plugins.json` | `schema: 1` | 坏了退化成"没确认过" | 安全侧行为正确，保留 |

## 2. 要解决的三件事

**① 降级必须被拒绝。** 新版本写的数据被旧版本读到，旧版本会把不认识的字扔掉、再整份写回 —— 那是**不可逆的数据丢失**。

**② 升级要有路径。** 「缺字段补默认值」只覆盖**形状**，不覆盖**语义**。`normalizeState` 里已经有一处手工兼容（把 `model` 从字符串升成对象那次），那种代码每改一次字段就长一段。

**③ 失败要可见。** checkpoint 版本不符现在是一条日志都没有的 `return null`。

## 3. 机制

### 3.1 一个统一的迁移入口：`src/config/migrate.ts`

```ts
interface Migration {
  from: number                              // 从哪个版本升
  describe: string                          // 一句话，进 warning
  apply: (data: unknown) => unknown         // 纯函数，不碰磁盘
}

migrate({ kind, current, raw, migrations }) => {
  data: unknown,
  from: number,
  to: number,
  applied: string[],     // 跑过哪些步骤（空 = 没迁移）
}
```

五条规则：

1. `version === current` → 原样返回，零开销
2. `version < current` → 按 `from` 递增依次 `apply`；**当前版本缺对应迁移就报错**（不能假装升级成功）
3. `version > current` → **抛 `DataTooNewError`**，调用方据此拒绝启动
4. 缺 `version` → 当作 `0`
5. 每一步之后校验版本确实前进了 1 —— 迁移函数把版本写错会当场炸，而不是把错误版本号写进文件

**为什么不提供 `--allow-newer-state` 强行打开**（设计初稿里写过这个开关）：
它等于允许旧代码读写新数据，而那正是这一节要防的唯一一件事。要么升级，要么把 `version` 手工改回去 —— 后者是一次明确的、有意识的动作。

### 3.2 落盘顺序

```
1. 读文件 → 迁移（纯内存）
2. 迁移成功且有实际步骤 → 先备份：state.json → state.json.v1.backup
3. 原子写新文件
4. 迁移失败 → 原文件一个字节都不动 + 报错 + 拒绝启动
```

备份名带**源版本**（`.v1.backup`）而不是时间戳：用户一眼能看出它是从哪一版来的。

### 3.3 事件日志永不迁移

`events.jsonl` 是 append-only 的事实记录。重写它 = 让「重放必须逐字一致」这条不变量作废。

所以规则是：**字段语义变了就新增事件类型，不改旧类型的含义**。读的一侧继续宽容（`rebuildMessages` 现在就是宽容的）。

### 3.4 checkpoint 的静默丢弃改成可见

`readCheckpoint()` 增加一个返回 warning 的版本，会话 init 把它并进 `InitResult.warnings`：

> 检查点版本 2 与当前 1 不符，已忽略 —— 会话会从事件日志重放重建，但那一刻的 turn/step 显示会从头开始。

## 4. 测试

```
版本相同 → 原样，applied 为空
缺 version → 当 0，走迁移
版本更新 → 抛 DataTooNewError，消息里有两个版本号
缺对应迁移 → 抛错（不是静默跳过）
迁移函数把版本写错 → 抛错
迁移抛错 → 原文件字节不变（按字节比对）
state.json v1 → v2 的假迁移：字段被改名且 version 前进
checkpoint 版本不符 → 返回 null 且带 warning
```

**诚实说明**：现在 v1 就是当前版本，**没有任何真实迁移要写**。这一节交付的是机制 + 一个用注入式 registry 证明它活着的测试。等真要改字段，写一个 `{ from: 1, describe, apply }` 即可。

# 二、令牌默认开

## 1. 现状

```
生成     token.ts：持久化到 <MVS_HOME>/host-token（48 位十六进制），重启复用
认同     Authorization: Bearer / ?token= / cookie 三种
cookie   HttpOnly + SameSite=Strict + Max-Age 7 天
默认     serve.ts  requireToken = false      ← 要改的就是这一个
测试     夹具默认 true（test/server.test.ts:157）
```

## 2. 为什么该默认开

`/command` 能执行命令、能写文件。而「只绑 127.0.0.1」**不构成认证**：同一台机器上任何进程都能连这个端口。

浏览器里其他站点的 JS 被三道围栏挡住（Host / Origin / `Sec-Fetch-Site` ✓），但**同机的非浏览器程序没有这三道** —— 它们自己填 header 就能声明自己是 localhost。

现状是：四道防线里写得最认真的那道（令牌），默认关着。

## 3. 改动

### 3.1 默认值

```
serve.ts     let requireToken = true
server.ts    options.requireToken ?? true
config       新增 server.requireToken?: boolean
优先级       命令行（--require-token / --no-token） > 配置 > 默认
```

### 3.2 启动横幅

默认从关变开，老用户第一次会愣一下，所以横幅必须自己解释：

```
令牌      开（首次打开用上面那条带 token 的地址；想关掉用 --no-token 或配置 server.requireToken=false）
```

### 3.3 锁不死自己：四条路径都要有测试

| 路径 | 要验的 |
|---|---|
| 无令牌打开 `/` | 401 + **说明页**（不是一句 JSON），且页面里**不含令牌** |
| 带 `?token=` 打开 | `/auth` 设 cookie 后跳转；cookie 有 HttpOnly + SameSite=Strict |
| cookie 过期（7 天后） | 重新点终端那条链接即可 —— 令牌持久化，所以链接一直有效 |
| WebSocket | 浏览器无法给 WS 设头，所以必须支持 `?token=` 升级 |

## 4. 明确不做

- **不做「仅本机免令牌」的例外**（按进程名/令牌白名单）：那要拿进程身份，Windows 上又回到限制型令牌那一套，项目已经明确不做
- **不做令牌轮换界面**：`--no-token` 与删掉 `host-token` 文件已经够了

# 三、实施顺序

1. **令牌默认开**：改动小（两个默认值 + 一个配置项 + 一行横幅），测试夹具默认已是 true，几乎不产生回归
2. **迁移机制**：`migrate.ts` + 三处接线 + 测试

两条互不依赖，各自可独立回滚。
